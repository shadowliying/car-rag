# 面试速背总纲

## 1. 项目一句话
这是一个面向汽车用户手册场景的封闭域智能问答系统，核心目标不是开放聊天，而是基于说明书对功能操作、参数配置、保养维护、安全提示和账户车机类问题做有依据的准确回答。

---

## 2. 整体链路
完整链路是：

- PDF 手册解析与分块
- `M3E + FAISS` 语义召回
- `BM25` 关键词召回
- 双路召回融合
- `BGE-reranker-large` 精排
- `Qwen-7B-Chat + vLLM` 生成答案
- 离线评测和压测验证效果

一句话概括：

> 先把文档变成知识块，再把相关块找出来、排准，最后让大模型基于证据组织答案。

---

## 3. 业务定位
这个项目不是通用聊天机器人，而是封闭域 RAG。

要点：

- 知识源主要来自汽车用户手册
- 用户高频问题包括功能操作、参数、保养、安全和账户车机
- 域外问题必须拒答
- 核心不是“什么都能答”，而是“有依据地答该答的问题”

最关键的一句话：

> 在这个场景里，正确回答和正确拒答同样重要。

---

## 4. PDF 解析与知识库
知识库构建是整个系统的地基。

要点：

- 原始数据大约 `50` 份 PDF
- 解析后形成约 `10000` 个 chunk
- 用了多策略分块：
  - `ParseBlock`
  - `ParseAllPage`
  - `ParseOnePageWithRule`
- 做了多粒度 chunk：`256 / 512 / 1024`
- overlap 用来减少步骤被切断
- 重点处理目录页、页码、警告说明、表格和图文混排

工具选型口径：

- 主口径可讲 `PaddleOCR`
- 因为汽车手册里图文混排、扫描页、表格较多，OCR 和版面分析能力重要
- 同时了解 `pdfplumber`、`pdfminer`、`PyPDF2`、`camelot`、`tabula`

最关键的一句话：

> 一个好的知识库不是“字都抽出来了”，而是“步骤不乱、参数不混、警告不丢”。

---

## 5. 召回模块
召回层的目标是：

- 不要漏掉真正相关的内容
- 尽量减少错误候选

采用的是双路召回：

- `M3E + FAISS` 做语义召回
- `BM25` 做关键词召回

为什么双路：

- Embedding 更适合口语 query、同义表达、长尾 query
- BM25 更适合缩写词、专有词、参数词、型号词

融合口径：

- 主流程：两路先各取 `Top15`
- 先合并去重，形成 `20~30` 个候选
- 再交给 Rerank
- 如果讲加权融合，可以说：
  - 分数先归一化
  - `final_score = 0.7 * vector + 0.3 * bm25`
  - 权重通过验证集调出来
  - 更理想是按 query 类型动态调权

---

## 6. Embedding 微调
这是召回模块最容易被深挖的点。

为什么要微调：

- 通用 Embedding 模型不够适配汽车领域
- 对缩写、参数项、相似概念区分不够稳
- 对长尾和口语 query 还有提升空间

训练数据：

- 主问答集约 `2000` 条
- 切分为 `1600/200/200`
- 从训练集构造约 `4200` 条三元组
- 格式：`(query, positive, hard negative)`

Hard Negative 很关键，例如：

- 机油容量 vs 机油更换周期
- 涉水前 vs 涉水后
- 驾驶员座椅 vs 副驾驶员座椅

损失函数：

- 主讲 `Triplet Loss`
- 本质是让 query 更靠近正确 chunk，远离相似但错误的 chunk

效果口径：

- Recall@10：`84.3% -> 87.2%`
- MRR：`0.62 -> 0.68`
- Top1：`52.3% -> 58.1%`
- Top3：`71.5% -> 76.2%`

训练曲线口径：

- train loss：`0.44 -> 0.32 -> 0.24 -> 0.19`
- 到第 `3` 个 epoch 基本平台
- 再训收益不大，容易过拟合

---

## 7. Rerank 模块
Rerank 的作用是：

**在候选集里把真正最相关的文档排到前面。**

为什么需要 Rerank：

- 召回负责海选，Rerank 负责精选
- 很多候选是“主题相关”但不一定“答案相关”

模型：

- `BGE-reranker-large`
- Cross-Encoder 结构
- Query 和 Doc 拼接后一起编码

为什么 Cross-Encoder 更准：

- Query 和 Doc 在编码阶段就充分交互
- 更擅长识别“很像但不对”的候选

为什么不能直接做全库召回：

- 太慢
- 所以只适合对 `20~30` 个候选做精排

---

## 8. Rerank 微调
这是第四类里最重要的部分。

为什么要微调：

- 通用 Rerank 只能做到一般相关性判断
- 但汽车场景里很多错误候选是 Hard Negative

训练方式：

- 最终采用 `Pointwise` 二分类
- 输入是 `(query, doc)`
- 标签是 `1/0`
- 损失函数用 `BCE Loss`

为什么不用 Listwise 作为主方案：

- 数据标注难
- 排序区分度不稳定
- 当前数据规模下性价比不高

数据口径：

- 核心人工标注 query 约 `200`
- 总样本约 `600`
- 正负比例 `1:2`

训练参数：

- epoch：`3`
- batch size：`16`
- lr：`2e-5`
- weight decay：`0.01`

效果口径：

- Accuracy：`82.3% -> 86.5%`
- Precision：`78.5% -> 80.5%`
- Recall：`85.2% -> 86.8%`
- F1：`81.7% -> 83.5%`

端到端效果：

- 无 Rerank：`84.2%`
- 有 Rerank 未微调：`86.6%`
- 有 Rerank 微调后：`88.6%`

---

## 9. 生成层与 Prompt
生成层的职责不是创造知识，而是：

- 基于召回和 Rerank 后的证据组织答案
- 控制输出格式
- 控制拒答
- 控制幻觉

Prompt 核心目标：

- 明确角色：汽车手册问答助手
- 明确知识来源：只能根据给定资料回答
- 明确拒答：找不到就输出“无答案”
- 明确输出规范：
  - 参数类简洁直给
  - 步骤类按顺序列点
  - 安全类保留注意事项

最关键的一句话：

> 生成层最重要的不是“更会说”，而是“更忠实、更稳定、该拒答时能拒答”。

---

## 10. LLM 微调
做过尝试，但最终没作为主方案。

口径：

- 尝试对 `Qwen-7B` 做过 SFT
- 数据规模约 `4000+` 条 QA
- 数据来源：
  - 种子问题
  - 现有 RAG 生成答案
  - GPT-4 扩写
  - 长上下文自动生成问答
  - 最后人工筛选

效果：

- 优点：格式更稳、字数更可控
- 缺点：长上下文总结能力下降
- 超过 `1~2` 个 epoch 容易 overfit

结论：

> 生成模型微调对格式控制有帮助，但不如“高质量检索 + Prompt 约束”稳定，所以最终没作为主方案。

---

## 11. 数据集与评测
整个项目的数据是分层构建的。

原始数据：

- 约 `50` 份 PDF
- 约 `10000` 个 chunk

主问答数据：

- 种子问题：`600`
- 扩写后：`2000`
- 切分：`1600/200/200`

派生训练数据：

- Embedding：`4200` 三元组
- Rerank：`600` 核心标注样本
- LLM SFT：`4000+` QA

评测分层：

- 召回：`Recall@K`、`MRR`
- Rerank：`Precision`、`F1`、`NDCG`
- 生成：关键词命中 + 语义相似度
- 端到端：系统准确率、拒答准确率

生成评测口径：

```text
Score = 0.5 * 关键词/实体词相似度 + 0.5 * 语义相似度
```

为什么这样做：

- 只看语义，数值可能错了也会被判高分
- 只看关键词，又会错杀合理改写

---

## 12. 部署与 vLLM
部署层的重点不是“模型能跑”，而是“高并发下稳定跑”。

为什么选 `vLLM`：

- 更适合在线推理服务
- KV Cache 管理更高效
- 并发调度更高效
- 吞吐更高

两个关键词：

- `PagedAttention`
  - 更高效管理 KV Cache
  - 降低显存浪费和碎片

- `continuous batching`
  - 请求动态进出 batch
  - 提高 GPU 利用率
  - 在线服务更合适

---

## 13. 压测与性能口径
压测分两层：

- 子服务压测：
  - Embedding
  - Rerank
- 端到端压测：
  - 多线程 client 模拟多用户

核心指标：

- 首字延迟
- 平均吞吐率
- 模块耗时拆分

统一口径：

- 最大并发：`512`
- 首字延迟：`~2s`
- 吞吐率：`~12k token/s`

模块耗时：

- BM25：`~10ms`
- 向量召回：`~30ms`
- Rerank：`~120ms`
- LLM 生成：`~1800ms`
- 总体：`~2000ms`

最关键的一句话：

> 这条链路里真正的性能瓶颈是 LLM 生成，不是召回，也不是 Rerank。

---

## 14. Badcase 排查框架
排查顺序一定要会背：

1. 知识库里有没有
2. 分块有没有切坏
3. 召回有没有召回来
4. Rerank 有没有排对
5. 生成有没有忠实表达

可以压缩成三类：

- 没找到
- 没排对
- 没说对

---

## 15. 典型 badcase
你至少要能举这些。

### 1. 机油容量 vs 机油更换周期
- 召回和 Rerank 的典型 Hard Negative

### 2. 涉水前 vs 涉水后
- 阶段边界混淆

### 3. 驾驶员座椅 vs 副驾驶员座椅
- 实体边界混淆

### 4. 蓝牙连接 vs 蓝牙版本说明
- 主题相关但意图不同

### 5. 步骤类问题漏步骤
- 多发生在分块或生成层

### 6. 域外问题拒答不稳
- 生成层和规则约束问题

### 项目总述
> 我做的是一个面向汽车用户手册的封闭域智能问答系统，整体采用 RAG 架构，核心链路是 PDF 解析分块、多路召回、Rerank 精排和大模型生成，重点解决车主在功能操作、参数配置、保养维护和安全提示上的高频问答问题。
