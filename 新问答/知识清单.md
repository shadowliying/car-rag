你现在最需要的不是再堆更多术语，而是把“文档里写的能力”补成一套能自圆其说的业务化表达。面试官真正在意的，不是你会不会背 `M3E`、`BGE-reranker`、`vLLM` 这些名词，而是你能不能把它们和汽车用户手册问答这个业务场景绑在一起，讲出为什么这么做、解决了什么问题、踩过什么坑、怎么验证有效。

我建议你按“项目口径统一 + 知识点补齐 + 实战问题清单”三层来准备。

**一、先统一你的面试口径**
你以后对外就按这条主线讲：

这是一个面向车主的智能座舱汽车知识问答系统，核心目标不是开放聊天，而是基于汽车用户手册，对功能操作、参数配置、保养维护、安全提示等问题做准确问答。整体链路是：

- PDF 手册解析成知识块
- 多路召回：`M3E + FAISS` 做语义召回，`BM25` 做关键词召回
- `BGE-reranker` 做精排
- `Qwen-7B-Chat + vLLM` 做答案生成
- 通过离线测试集和压测验证效果

这个口径的关键点有三个：

- 你讲的是“封闭域知识问答”，不是“通用聊天机器人”
- 你讲的是“有业务目标的 RAG 系统”，不是“把 PDF 扔给大模型”
- 你讲的是“实际做过评测、优化、压测和 badcase 分析”，不是只做了 demo

**二、你需要重点补齐的知识点清单**
下面这份不是泛泛知识点，而是为了让你在问答里显得像真的做过。

**1. 业务理解层**
你必须真的懂这些：

- 为什么车主不会自己翻说明书，而需要问答系统
- 车主高频问题的类型有哪些
- 为什么这个业务场景对“准确率”和“拒答能力”要求高
- 为什么“域外问题拒答”比“尽量回答”更重要
- 这个项目服务的是谁：车主、售后、客服、车机端智能助手

你要能顺口举出的业务问题类型：

- 功能操作类：怎么连蓝牙、怎么开座椅加热、怎么调 HUD
- 参数配置类：机油容量、屏幕尺寸、后备箱容积
- 保养维护类：什么时候打蜡、涉水后检查什么
- 安全告警类：安全气囊、儿童锁、HDC、FCTA
- 异常处理类：车辆故障、涉水、刹车异响
- 账户与车机类：Lynk&Co ID、人脸识别、亲情账号、偏好同步

**2. 数据与知识库层**
你要补齐：

- PDF 手册为什么不能整本直接塞给 LLM
- 为什么要 chunk
- `256/512/1024` 多粒度 chunk 的意义
- `ParseBlock`、`ParseAllPage`、`ParseOnePageWithRule` 各自解决什么问题
- 滑窗 overlap 为什么重要
- 为什么步骤类内容、参数表、跨页内容最容易出问题
- 为什么目录页、页码、重复块、警告说明要特殊处理

你必须能解释的实际问题：

- “涉水后需要检查哪些项目”这种连续步骤为什么容易被切碎
- “什么时候应该为车辆打蜡”这种保养类说明为什么要保留上下文
- “机油容量是多少”这种参数类问题为什么最好能命中表格行或短段落
- “ACC/HDC/FCTA”这类缩写在手册里为什么要保留原词，不能乱改写

**3. 召回层**
你要真正补齐：

- 向量召回和 BM25 的差异
- 为什么要双路召回，不是一条链路走到底
- FAISS 做了什么
- BM25 为什么对专有词、缩写、型号词更友好
- 哪些 query 更适合向量召回，哪些更适合 BM25
- 多路召回怎么合并、去重、截断
- topK 为什么不是越大越好

你要能举出的业务化例子：

- “咋连蓝牙”  
向量召回更有优势，因为这是口语表达和文档表达不一致的问题
- “HDC 是什么”  
BM25 更稳，因为缩写命中很关键
- “涉水后检查什么”  
双路召回更稳，既有关键词，也有步骤描述
- “车主账户怎么创建”  
如果 query 里有 `Lynk&Co ID` 这种专名，BM25 兜底很重要

**4. Rerank 层**
你要补：

- 为什么召回后还需要重排
- `bi-encoder` 和 `cross-encoder` 差别
- Rerank 的业务价值是什么
- 为什么给 LLM 的上下文不能太多
- Rerank 提升的是哪一段能力：从“召回相关”变成“挑最相关”

你要能讲的实际问题：

- 用户问“如何开启座椅加热”，召回出来了“座椅”“空调”“舒适配置”很多内容，Rerank 的作用就是把真正有操作步骤的段落顶上来
- 用户问“什么是转向助力系统”，如果上下文混进一堆涉水、转向检查、方向盘调节内容，LLM 很容易答偏，Rerank 就是在减少这种噪音

**5. LLM 生成层**
你要补：

- Prompt 为什么要明确“只根据资料回答”
- 为什么要允许输出“无答案”
- 温度、生成长度、束搜索这类参数的大概作用
- 为什么生成层不是“模型越大越好”，而是要看延迟、吞吐、业务体验
- 为什么错误上下文会直接放大幻觉

你要能讲的业务问题：

- 对“中国足球的队长是谁”“新冠肺炎如何预防”这类域外问题，系统要拒答
- 对“车机支持不支持某个外部功能”而手册没写的，也应该拒答
- 对“数值类答案”，比如容量、尺寸、周期，不能靠模型脑补

**6. 评测层**
你要补齐：

- 为什么生成式问答不能只看 BLEU/ROUGE
- 为什么要同时看关键词命中和语义相似度
- 什么叫“答对”
- 什么叫“答得像但其实错”
- 测试集为什么要覆盖口语问法、半截问法、参数类、步骤类、域外类

你要能说清的实际评测维度：

- 参数类：数值对不对
- 操作类：步骤全不全、顺序对不对
- 定义类：概念有没有讲偏
- 域外类：是否正确拒答
- 结果类：有没有幻觉、有没有混入错误实体

**7. 部署与性能层**
你要补：

- vLLM 的核心价值是什么
- `PagedAttention` 是怎么提高 KV Cache 利用率的
- `continuous batching` 为什么对并发友好
- 首 token 延迟和吞吐量分别代表什么
- 为什么 7B 模型在单卡可部署时，多实例并发可能比 TP 更划算
- 为什么 Docker 是环境交付问题，不是算法问题

你要能结合业务讲：

- 车机问答要求响应别太慢，用户不会等 8 秒
- 检索和重排只是前菜，生成才是主要延迟来源
- 高并发时，如果生成太慢，用户会觉得“系统卡”
- 如果成本受限，模型、并发、延迟要做平衡

**8. Badcase 与迭代层**
这是你最需要像“真实做过”的部分。你必须补：

- badcase 排查路径
- 如何区分是分块问题、召回问题、重排问题、生成问题
- 如何做 query 归一化、缩写映射、口语改写
- 为什么长尾 query 难
- 为什么数字、部件名、功能缩写特别容易出错

你要能讲的典型 badcase：

- 问“靠背太热怎么办”，结果答成通风而不是关闭加热
- 问“涉水后检查什么”，漏了“转向助力”
- 问“ACC 怎么开”，被错误改写成空调
- 问“机油容量”，召回成“机油更换周期”
- 问“蓝牙咋连”，没召回到“蓝牙连接指南”

**四、为了让你“像真正落地过”，你要重点补的实战表达**
你回答时不要只说“我用了什么”，要用下面这种结构：

- 业务问题是什么
- 为什么原方案不够
- 我怎么改
- 改完带来了什么变化
- 还有什么代价或局限

比如不要说：
“我用了 BM25 和 FAISS。”

要说：
“因为车主问题里既有口语化表述，也有很多专有名词和缩写。如果只做向量召回，像 `ACC`、`HDC` 这种精确词可能不稳；如果只做 BM25，像‘咋连蓝牙’这种口语 query 又容易召回不到。所以我用了 `M3E + FAISS` 做语义召回，BM25 做关键词兜底，两路合并后再做 rerank，这样既能覆盖口语问题，也能保住缩写和型号词。”

再比如不要说：
“我做了 PDF 分块。”

要说：
“汽车手册里很多问题不是单句答案，而是一段连续步骤，比如涉水检查、账号创建、功能开启。如果切块太粗，检索不准；切块太细，步骤会被切断。所以我做了多粒度 chunk 和滑窗分块，用 overlap 保证步骤连续性，这样步骤类问题和参数类问题都能兼顾。”
