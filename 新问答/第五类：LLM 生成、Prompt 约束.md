
# 第五类：LLM 生成、Prompt 约束、拒答与幻觉控制

这一类是整个项目里最容易被面试官拿来判断你“有没有产品和工程意识”的部分。  
因为前面的 PDF 解析、召回、Rerank 解决的是“能不能把相关资料找出来”，而这一类解决的是：

**找出来之后，怎么让大模型稳定、可控、符合业务地把答案说出来。**

这一层最常见的误区是把它讲成：

- “最后接了个 Qwen”
- “写了个 Prompt”
- “让它回答用户问题”

这样会显得非常浅。  
面试官真正想听的是：

- 为什么已经有检索结果了，还需要 LLM
- 为什么不是直接把召回结果原样返回
- Prompt 到底怎么约束
- 如何避免编造
- 域外问题怎么拒答
- 数值类、步骤类、安全类问题怎么控制输出
- 有考虑过对 LLM 做微调吗
- 为什么最后采用或没采用 SFT
- 生成层的 badcase 是什么
- 如何判断是“检索错了”还是“模型编了”

所以这一类你要讲成：

**LLM 不是来“自由发挥”的，而是来基于召回证据做受约束的答案组织。**

---

## 一、这一类你要掌握到什么程度

你至少要做到：

1. 能讲清生成层在整个 RAG 里的角色。
2. 能讲清为什么不能让 LLM 裸答，也不能把召回结果直接原样返回。
3. 能讲清 Prompt 的设计目标。
4. 能讲清什么叫“基于资料回答”和“拒答”。
5. 能讲清如何控制幻觉、如何处理域外问题。
6. 能讲清步骤类、参数类、安全类问题在生成侧的不同要求。
7. 能讲清生成参数为什么要偏保守。
8. 能讲清是否尝试过 LLM 微调，以及为什么最终没作为主方案。
9. 能讲清生成层会出现哪些真实 badcase。
10. 能讲清生成层和召回层、Rerank 层的边界。

---

## 二、生成层在整个系统里的作用是什么

生成层不是用来“替代检索”的，而是用来：

**把检索和重排后的证据，组织成用户能直接看懂、能直接用的答案。**

它解决的是三个问题：

### 1. 文档原文不一定适合直接返回
用户不想看一堆原始 chunk，尤其是说明书语句通常偏书面、偏分散。

### 2. 一个问题的答案可能分散在多个证据块里
例如：

- 一个 chunk 讲定义
- 一个 chunk 讲操作步骤
- 一个 chunk 讲注意事项

LLM 可以把这些信息组织成更完整的最终回答。

### 3. 回答需要更贴近用户表达
比如用户问：

- `咋连蓝牙`

系统最终不能只返回“蓝牙连接方式”这几个字，而应该输出更自然的步骤化答案。

所以生成层的职责不是“创造知识”，而是：

> 对已有证据做整理、压缩、改写和输出控制。

---

## 三、为什么不能直接让 LLM 裸答

这是高频问题。

原因有四个。

### 1. 汽车场景错误成本高
如果模型自由发挥，涉及：

- 安全功能
- 故障处理
- 参数数值
- 保养建议

一旦答错，风险比普通聊天高很多。

### 2. 知识边界是封闭的
这个项目的知识源主要是汽车用户手册，不是开放世界。  
所以系统必须表现得像一个“基于手册回答的助手”，而不是一个百科全书。

### 3. 裸答会带来更强幻觉
特别是当问题看起来像车相关，但手册里并没有明确答案时，模型很容易补全。

### 4. 裸答不可控
你很难保证：

- 格式统一
- 字数合适
- 数字不乱编
- 找不到答案时会老实承认

所以生成层必须建立在检索证据之上。

---

## 四、为什么又不能只把召回结果直接返回

这也是一个很好的追问点。

因为如果只返回原文 chunk，会有三个问题：

### 1. 用户成本仍然高
用户还是得自己读、自己理解、自己拼信息。

### 2. 多个 chunk 之间没有被组织
如果答案分布在 3 个 chunk 里，直接返回片段会让用户更乱。

### 3. 说明书表达不一定适合用户提问方式
用户问的是场景化问题，文档写的是章节化、说明书化语言。

所以 RAG 的价值就在于：

> 检索负责找依据，LLM 负责把依据组织成用户可消费的答案。

---

## 五、这一层的核心目标不是“自然”，而是“忠实、可控、稳”

你一定要建立这个意识：

这个项目的生成层不是写作文，也不是情感陪伴，不是越像人越好。  
更重要的是：

- 忠实于证据
- 不乱扩写
- 不乱补全
- 该拒答就拒答
- 对数值和步骤保持稳定

所以生成层优化方向和开放聊天完全不一样。  
这里最重要的不是“文风多好”，而是：

> 回答有没有依据、有没有越界、有没有把真正需要的信息说完整。

---

## 六、Prompt 的核心设计目标

Prompt 设计不只是“给模型一个任务描述”，而是整个生成层最核心的控制手段。

在这个项目里，一个好的 Prompt 至少要做到五件事：

### 1. 明确角色
告诉模型：

- 你是汽车用户手册问答助手
- 不是通用聊天助手

### 2. 明确知识来源
告诉模型：

- 只能基于提供的上下文回答
- 不能用外部常识补全

### 3. 明确拒答条件
告诉模型：

- 如果上下文不足或没有答案，要输出“无答案”或类似固定口径

### 4. 明确输出风格
比如：

- 参数类问题要简洁
- 步骤类问题要分点
- 安全类问题要保留警示信息

### 5. 明确不要编造
尤其是：

- 数值
- 零部件名
- 功能名
- 触发条件
- 支持/不支持类结论

---

## 七、一个合理的 Prompt 设计思路

你不一定要背完整 Prompt，但你要会讲设计逻辑。

可以分成四层。

### 1. 系统角色层
例如：

- 你是一个基于汽车用户手册的问答助手
- 只能根据提供资料回答问题

### 2. 任务约束层
例如：

- 优先依据上下文
- 找不到就回答“无答案”
- 不允许编造不存在的信息

### 3. 输出规范层
例如：

- 答案简洁、准确、易懂
- 步骤类按顺序列出
- 参数类优先给核心值
- 安全提示要保留

### 4. 用户问题与上下文层
把：

- 用户 query
- Rerank 后 Top-K context

一起送进去。

---

## 八、不同类型问题，Prompt 约束重点不一样

这是很加分的一点。

### 1. 参数类问题
例如：

- 机油容量是多少
- USB 接口有几个
- 屏幕尺寸多大

Prompt 重点：

- 直接回答核心数值
- 不要过度展开
- 不要补充上下文中没有的参数

### 2. 步骤类问题
例如：

- 怎么连接蓝牙
- 怎么创建 Lynk&Co ID
- 涉水后检查什么

Prompt 重点：

- 按步骤输出
- 顺序清晰
- 不漏关键条件和注意事项

### 3. 定义类问题
例如：

- HDC 是什么
- 转向助力系统是什么

Prompt 重点：

- 先定义
- 再补作用或使用条件
- 不要说成泛泛百科解释

### 4. 安全类问题
例如：

- 儿童锁怎么开启
- 安全气囊相关问题
- 涉水驾驶相关注意事项

Prompt 重点：

- 不能只给操作，不给警示
- 需要保留“注意/警告/说明”中的关键内容

### 5. 域外问题
例如：

- 中国足球的队长是谁
- 新冠肺炎如何预防

Prompt 重点：

- 稳定拒答
- 不尝试迁就回答

---

## 九、拒答机制为什么重要

这部分一定要讲好，因为它最体现产品边界意识。

### 1. 拒答不是能力不足
在这个场景里，拒答反而是专业性的体现。

### 2. 为什么必须拒答
因为如果知识库没有，模型又强答，就会出现“看起来很像真的”的错误答案。

### 3. 哪些情况应该拒答
至少包括：

- 域外问题
- 资料中没有答案
- 问题和上下文相关度过低
- 用户问的是猜测性、未来性、实时性问题

### 4. 拒答口径要统一
比如：

- `无答案`
- `未在提供资料中找到相关信息`

不能一会儿拒答，一会儿又开始泛泛聊。

---

## 十、如何判断该回答还是该拒答

这是很实战的问题。

在实际系统里，通常不会只看 LLM 自己判断，而会结合前面的检索信号。

可以从三层看：

### 1. 检索层信号
如果：

- 召回结果很差
- 候选数量太少
- 候选相关度很低

那就说明回答风险高。

### 2. Rerank 层信号
如果：

- Top1 分数很低
- TopK 分数分布很散
- 没有明显强相关 chunk

也更适合拒答。

### 3. Prompt 约束
最后再通过 Prompt 明确要求：

- 上下文不足则输出“无答案”

你可以这样讲：

> 实际上拒答不是只靠 LLM 的自觉，而是结合召回质量、Rerank 分数和 Prompt 约束共同实现的。这样比单纯让模型自己判断更稳。

---

## 十一、生成层怎么控制幻觉

这是这一类最核心的面试点之一。

幻觉控制主要靠下面几种手段。

### 1. 证据约束
只把 Rerank 后最相关的少量 chunk 给模型，减少噪音。

### 2. Prompt 约束
明确写：

- 仅根据资料回答
- 资料不足就拒答
- 不得编造

### 3. 输出风格约束
比如：

- 参数类只给值
- 步骤类按列表输出
- 安全类保留注意事项

### 4. 控制生成随机性
不要把温度设太高。

### 5. 缩短上下文
上下文太长、太杂，本身就会放大幻觉。

所以一句话：

> 幻觉控制不是只靠 Prompt，而是“高质量检索 + 少量高相关上下文 + 保守生成参数 + 明确拒答规则”的组合。

---

## 十二、生成参数为什么要偏保守

在这个项目里，一般不应该追求特别开放、特别发散的生成。

更合理的口径是：

- `temperature` 设低一些，比如 `0.1 ~ 0.3`
- `top_p` 不要太激进
- `max_new_tokens` 控制在合理范围
- 输出追求稳定，不追求花哨

原因很简单：

- 这是业务问答，不是创作任务
- 数字和步骤不能飘
- 安全相关问题不能乱扩写

所以你可以说：

> 这个项目的生成参数设计是偏保守的，因为目标是稳定和忠实，不是开放式发挥。

---

## 十三、为什么选择 Qwen-7B-Chat 作为生成模型

这部分你可以讲得简洁但有逻辑。

主要原因：

1. 中文能力比较好
2. 指令跟随能力不错
3. 本地部署可行
4. 和当前 RAG 场景匹配较好
5. 在成本、效果和部署复杂度之间平衡合理

如果面试官问为什么不是更大模型，可以答：

- 更大模型当然可能更强
- 但这个项目是完整工程系统，不只是单次 demo
- 要同时考虑推理速度、显存、并发和部署成本

## 十四、有没有尝试过对 LLM 做微调

这一块是本类最值得准备的重点之一。  
因为你们资料里是明确提过“尝试过，但最终没作为主方案”的。

你可以这样统一口径：

### 1. 做过尝试
对 `Qwen-7B` 做过 SFT 微调。

### 2. 数据大概多少
构造了 `4000+` 条 `[Q, A]` 训练语料。

### 3. 数据怎么来
可以按这个口径讲：

- 先写一些种子问题
- 用现有 RAG 系统生成一部分答案
- 再用 GPT-4 对问题和答案做扩写和泛化
- 也尝试过输入上下文长文本，让 GPT-4 帮忙生成问答
- 最后再人工筛选一遍

### 4. 微调后观察到什么
优点：

- 答案格式更可控
- 字数更容易控制
- 输出风格更统一

缺点：

- 长上下文总结能力反而下降
- 对复杂文档整合型问题不如原生模型
- epoch 稍微多一点就容易 overfit

### 5. 最终为什么没采用
核心原因：

- 数据量和数据质量还不足以支撑生成模型稳定提升
- 过度微调会损伤原模型的通用总结能力
- 当前阶段“RAG 检索质量 + Prompt 控制”收益更稳定

这一段非常重要，你可以直接背：

> 我们对 Qwen-7B 做过 SFT 尝试，大概构造了 4000 多条 QA 数据。微调后的好处是格式更可控、答案长度更稳定，但长上下文总结能力反而变差了，尤其是跨 chunk 的信息整合不如原生模型。训练超过 1 到 2 个 epoch 后还有明显过拟合倾向，所以最终没有把生成模型微调作为主方案，而是保留基础模型，重点优化检索、Rerank 和 Prompt 约束。

---

## 十五、为什么生成模型微调没成为主收益点

这句话很像面试官会追问你。

答案是：

> 在这个项目里，生成层的上限更多取决于“给模型喂了什么上下文”，而不是单纯“把模型调得更会说”。

也就是说：

- 上下文不准，模型越会说越危险
- 上下文准，基础模型通过好 Prompt 已经能做得不错

所以相比盲目 SFT，当前阶段更高性价比的是：

- 提升召回
- 提升 Rerank
- 控制 Prompt
- 做拒答机制

这会显得你对整个系统优先级很清楚。

## 十六、生成层最常见的 badcase

### badcase 1：召回相关，但模型总结错重点
例如用户问：

- `涉水后需要检查什么`

上下文里明明有多项检查内容，但模型最后只总结出两三项。  
这通常不是知识库没有，而是：

- 上下文太长
- 重点被稀释
- 模型压缩时漏信息

### badcase 2：把“相关内容”说成“正确答案”
例如：

- 用户问机油容量
- 模型把机油更换周期混进答案

这是典型的“错误上下文放大”。

### badcase 3：数值类问题轻微编造
例如：

- 文档只给了部分参数
- 模型把缺失值补成了一个看起来合理的数字

这类在业务上很危险。

### badcase 4：步骤类问题漏步骤或顺序错
例如：

- 创建账号步骤漏掉绑定环节
- 蓝牙连接步骤顺序混乱

### badcase 5：域外问题拒答不稳
例如：

- 问天气、体育、医疗问题时，模型还是想顺着聊下去

### badcase 6：安全类问题只说操作，不说警示
例如：

- 只告诉你怎么开某功能
- 但没告诉你什么情况下不能开

这在业务上是不够的。

---

## 十七、如何排查是生成层的问题，还是上游问题

这也是很实战的排查思路。

### 1. 先看知识库里有没有
没有的话，不是生成层问题。

### 2. 再看召回和 Rerank 结果对不对
如果送给模型的上下文本身就错了，那问题主要不在生成层。

### 3. 如果上下文是对的，但答案仍然错
这时才重点怀疑生成层，例如：

- Prompt 不够约束
- 上下文太长
- 格式要求不清楚
- 模型压缩时丢信息

你可以这样讲：

> 生成层的问题通常是在“证据基本正确，但最终表达不忠实”时才成立；如果证据本身就错了，那更应该先回头排查召回和 Rerank。

## 十八、这一类最可能被问到的完整问答

### Q1：生成层在你们项目里主要负责什么？

**答：**  
生成层主要负责把召回和重排后的证据组织成用户可读答案。它不是负责找知识，而是负责基于已有证据做整理、压缩和输出控制。因为说明书原文不一定适合直接返回，而且一个问题的答案可能分散在多个 chunk 里，所以需要 LLM 来做最终组织。

### Q2：为什么不能直接让大模型裸答？

**答：**  
因为这个项目是汽车用户手册问答，属于封闭域业务场景，错误成本比较高。如果让模型裸答，它很容易调用通用常识去补全，尤其在安全、保养、参数和故障处理类问题上风险很大。我们希望它像一个“基于手册回答的助手”，而不是一个开放式聊天机器人，所以必须建立在检索证据之上。

### Q3：为什么又不能只把召回结果直接返回？

**答：**  
因为用户还是需要自己读和自己拼信息，体验并没有真正提升。而且很多答案分散在多个 chunk 里，直接返回原文会让信息更碎。LLM 的价值就在于把这些证据组织成更完整、更易理解、更符合用户提问方式的答案。

### Q4：Prompt 设计的核心目标是什么？

**答：**  
核心有四个：第一，明确角色，它是汽车手册问答助手；第二，明确知识来源，只能基于提供的上下文回答；第三，明确拒答规则，找不到答案时要输出“无答案”；第四，明确输出风格，比如步骤类按顺序列点、参数类简洁直给、安全类保留注意事项。Prompt 的本质不是让模型更会说，而是让模型更可控。

### Q5：你们是怎么控制幻觉的？

**答：**  
幻觉控制不是只靠一句“不要编造”，而是多层一起做。前面先用召回和 Rerank 控制上下文质量，只给模型少量高相关 chunk；Prompt 再明确要求只能依据资料回答，资料不足就拒答；同时生成参数设置得比较保守，避免随机性太强。也就是说，幻觉控制依赖的是“高质量证据 + 明确约束 + 保守生成”。

### Q6：域外问题怎么处理？

**答：**  
域外问题要稳定拒答。因为这个系统是封闭域问答，不是通用聊天。像“中国足球的队长是谁”“新冠肺炎如何预防”这种问题，不在手册知识范围内，就应该返回“无答案”或者“未在提供资料中找到相关信息”，而不是尝试给出一个看起来合理的回答。

### Q7：怎么判断该回答还是该拒答？

**答：**  
不是只让 LLM 自己判断，而是结合前面检索和重排的信号。如果召回结果很弱、Rerank Top1 分数低、上下文覆盖不足，那说明强答风险很高，这时候更适合拒答。最后再通过 Prompt 明确要求资料不足时输出“无答案”。这样会比单纯依赖模型主观判断更稳定。

### Q8：生成参数为什么要设置得偏保守？

**答：**  
因为这是业务问答，不是创作场景。我们更关心的是答案忠实、稳定、不乱编，尤其是数值、步骤和安全提示不能飘。所以生成时一般会把温度设低一些，比如 0.1 到 0.3 这个级别，控制输出更稳定，而不是追求发散性。

### Q9：你们有没有尝试对 Qwen 做微调？

**答：**  
有尝试过。我们构造了 4000 多条问答数据，对 Qwen-7B 做过 SFT 微调。数据来源包括种子问题、基于现有 RAG 生成的答案、GPT-4 扩写后的问题答案，以及从长上下文生成的问答对，再经过人工筛选。微调后的好处是格式更可控、字数更稳定，但长上下文总结能力反而下降，跨 chunk 的信息整合变差，而且训练超过 1 到 2 个 epoch 就容易过拟合，所以最后没有把它作为主方案。

### Q10：为什么最后没采用 LLM 微调，而是继续用 Prompt + RAG？

**答：**  
因为这个项目里生成层的效果上限更依赖前面喂给模型的上下文质量，而不是单纯把模型调得更会说。我们实际验证下来，RAG 检索质量和 Prompt 控制带来的收益更稳定，而生成模型微调虽然能改善格式，但会损伤长上下文总结能力，性价比不高，所以最后还是保留基础模型，重点优化检索、Rerank 和生成约束。

### Q11：生成层最典型的 badcase 是什么？

**答：**  
最典型的是两类。第一类是上下文基本对，但模型总结时漏掉关键信息，比如步骤类问题漏步骤、涉水检查漏检查项；第二类是上下文里有相似内容，模型把“相关但不对”的信息混进答案，比如把机油更换周期混进机油容量问题。这类问题说明生成层不能脱离上游证据质量单独看。

### Q12：怎么判断问题出在生成层而不是召回层？

**答：**  
先看送给模型的上下文。如果上下文本身就是错的，那问题主要在召回或 Rerank；如果上下文基本正确，但最终答案仍然漏信息、错总结、乱补全，那才重点看生成层，比如 Prompt 是否不够约束、上下文是否过长、输出要求是否不清楚。我的排查顺序一般是知识库 → 召回 → Rerank → 生成。

## 十九、这一类最容易犯的错误

1. 把生成层讲成“最后接了个大模型”。
2. 只会说 Prompt 很重要，但说不出 Prompt 到底约束什么。
3. 不会区分“回答能力”和“拒答能力”。
4. 不会解释为什么封闭域场景下拒答很关键。
5. 只讲模型，不讲数值类、步骤类、安全类问题的差异。
6. 不会把生成 badcase 和上游检索问题区分开。
7. 说做过 LLM 微调，但讲不清数据来源和为什么最后没采用。
8. 把生成层目标说成“更自然”，而不是“更忠实、更可控”。

## 二十、这一类的最终背诵版总结

> 在这个项目里，生成层的作用不是创造知识，而是把召回和 Rerank 后的证据组织成用户可读的最终答案。因为说明书原文往往分散、书面化，而且一个问题的答案可能分布在多个 chunk 里，所以需要 LLM 做整理和表达。但这个场景是封闭域汽车手册问答，重点不是让模型自由发挥，而是让它基于证据忠实回答，因此 Prompt 的核心是明确角色、限定知识来源、要求资料不足时拒答，并约束输出风格。对于参数类、步骤类、安全类问题，生成层的要求也不同：参数类要直接、步骤类要按顺序、安全类要保留警示信息。  
> 我们生成模型用的是 Qwen-7B-Chat，也尝试过做 SFT 微调，大概构造了 4000 多条 QA 数据。微调后格式和字数更可控，但长上下文总结能力变差，训练超过 1 到 2 个 epoch 还容易过拟合，所以最终没有把 LLM 微调作为主方案，而是保留基础模型，重点优化检索、Rerank、Prompt 约束和拒答机制。对这个项目来说，生成层最重要的不是“更会说”，而是“更忠实、更稳定、该拒答时能拒答”。
