
# 第三类：召回模块设计、BM25、FAISS 与 Embedding 模型微调

这一类是整个项目里最容易被深挖、也最容易拉开差距的一类。  
因为面试官一般不会满足于你说“我们用了 `M3E + FAISS + BM25`”，他真正想听的是：

- 你为什么这样设计召回链路
- `BM25` 和向量召回分别解决什么问题
- `FAISS` 在里面到底干什么
- 为什么通用 Embedding 模型还不够，必须做微调
- 微调的数据怎么构造
- `Hard Negative` 为什么关键
- 损失函数、训练指标、停训标准你是不是真的懂
- 微调后到底带来了什么变化

所以这一类你不能讲成工具堆砌，而要讲成：

**围绕汽车手册问答这个业务场景，如何把真正相关的知识块稳定召回出来。**

---

## 一、这一类你要掌握到什么程度

你至少要做到：

1. 能讲清召回层在整个 RAG 里的角色。
2. 能讲清 `BM25` 的原理、优缺点和适用 query。
3. 能讲清 `Embedding + FAISS` 的原理、优缺点和适用 query。
4. 能讲清为什么一定要做多路召回。
5. 能讲清为什么选择 `M3E-large` 作为 Embedding 基座。
6. 能讲清为什么要做 Embedding 微调。
7. 能讲清训练数据怎么构造，尤其是 `Hard Negative`。
8. 能讲清 `Triplet Loss` 和 `InfoNCE` 的直觉。
9. 能讲清训练时怎么看 `loss`、怎么看 `Recall@K`、什么时候停。
10. 能讲清训练过程中遇到过什么真实问题，以及怎么修。
11. 能把所有技术点都和业务场景绑起来，而不是空谈模型。

---

## 二、召回层在整个系统里的作用

召回层的任务不是直接回答问题，而是：

**从知识库里先找出一批最可能相关的候选 chunk。**

整个链路可以理解成：

- PDF 解析与知识库构建：把知识准备好
- 召回：从大规模 chunk 中先找到“可能对”的内容
- Rerank：从“可能对”里挑“最对”的内容
- LLM：基于这些内容生成用户可读答案

所以召回层的核心目标只有两个：

- 不要漏掉真正相关的内容
- 尽量别把太多错误内容带进来

召回层一旦出问题，会有三种后果：

1. 没召回来  
真正答案所在 chunk 根本没进候选池，后面模块无能为力。

2. 召回错了  
召回的是相似但不对的内容，比如“机油更换周期”代替“机油容量”。

3. 召回太杂  
正确内容有，但噪音太多，后续 Rerank 和 LLM 容易被误导。

所以一句话概括：

> 召回层决定了后面模型到底能看见什么信息。

## 三、为什么要做多路召回

汽车手册场景里的用户 query 并不统一，至少有四类典型形态。

### 1. 口语化 query
例如：

- 咋连蓝牙
- 靠背太热怎么办
- 怎么把车开暖一点
- 那个灯怎么关

这类 query 往往和手册里的标准写法不一样，更适合 **Embedding 语义召回**。

### 2. 缩写词 / 专有词 query
例如：

- ACC 怎么开
- HDC 是什么
- FCTA 的作用
- Lynk&Co ID 怎么创建

这类 query 更依赖词面精确命中，更适合 **BM25**。

### 3. 参数类 query
例如：

- 机油容量是多少
- USB 接口有几个
- 屏幕尺寸多大

这类 query 既需要精确字段命中，也需要一定语义能力，通常需要 **BM25 和 Embedding 共同覆盖**。

### 4. 长尾复杂 query
例如：

- 副驾娱乐屏的 HDMI 接口支持 4K 输出吗
- 方向盘助力与驾驶模式联动怎么开

这类 query 需要 Embedding 的泛化能力，也需要 BM25 做关键词兜底。

所以这个项目不能只用单一路线，而是：

**`BM25 + Embedding` 多路召回，然后交给 Rerank 精排。**

这句话你要记住：

> 多路召回不是为了炫技，而是因为不同检索方法擅长解决不同类型的业务 query。

### 5. 两路召回结果怎么融合

这一点面试里很容易被追问。

最稳的工程口径是：

- `BM25` 先取 `Top15`
- `M3E + FAISS` 先取 `Top15`
- 两路结果先做 `合并去重`
- 合并后大约得到 `20~30` 个候选
- 再交给后续 `Rerank` 做精排

也就是说，**主流程上我们更强调先 union，再精排**，而不是在第一层就把两个分数硬融合成最终排序。

这么做有三个原因：

1. `BM25` 分数和向量相似度分数不在一个量纲上，直接相加不稳定。
2. 召回层的第一目标是覆盖率，也就是尽量别漏掉真正答案，而不是在这一层就把排序做死。
3. 后面已经有 `Rerank`，所以第一层更适合做候选扩充，第二层再做精细排序。

所以你在面试时可以先这样说：

> 我们主流程里，BM25 和向量召回各自先取 Top15，然后先合并去重，把候选池扩到 20 到 30 个，再交给 Rerank 精排。因为召回层更重要的是覆盖率，而 BM25 和向量分数本身分布不同，第一层直接硬加权不一定稳定，所以先 union 再精排是更稳的方案。

### 6. 如果要做加权融合，怎么做

如果面试官继续追问“那你们有没有做过加权融合”，你可以再往下讲。

加权融合的前提是：**先做分数归一化**。

因为：

- `BM25` 分数来自词频统计
- 向量召回分数来自余弦相似度或内积

这两类分数的取值范围和分布都不同，不能直接相加。

比较常见的做法是先做归一化，例如：

- `min-max normalization`
- `z-score normalization`

然后再做加权：

```text
final_score = α * vector_score + (1 - α) * bm25_score
```

在这个项目里，更合理的口径是：

- 向量召回作为主路
- BM25 作为精确词兜底

所以如果要给一个固定权重，通常会让向量召回更高，比如：

```text
α = 0.7
final_score = 0.7 * vector_score + 0.3 * bm25_score
```

### 7. 为什么向量召回权重更高

因为这个项目里用户 query 有很大一部分是：

- 口语化表达
- 同义改写
- 长尾自然语言描述

这类问题 Embedding 的泛化能力更强，所以它更适合做主路。

而 BM25 更适合做：

- 缩写词命中
- 参数词命中
- 专有词和型号词兜底

所以整体上是：

> 向量召回负责主覆盖，BM25 负责精确术语兜底，因此固定权重方案里通常让向量权重更高。

### 8. 权重是怎么确定的

这一点不要回答成“凭经验拍的”，更好的说法是：

> 权重是在验证集上调出来的，不是主观设定的。

比较稳的调参流程是：

1. 固定两路召回的候选规模，例如都取 `Top15`
2. 对 `BM25` 和向量分数分别做归一化
3. 在验证集上扫描不同权重组合，例如：
   - `0.5 / 0.5`
   - `0.6 / 0.4`
   - `0.7 / 0.3`
   - `0.8 / 0.2`
4. 观察指标：
   - `Recall@20`
   - `MRR`
   - 端到端准确率
5. 选综合效果最好的权重

比较自然的项目口径可以讲成：

> 我们做过归一化后的加权实验，最后发现 `0.7 / 0.3` 这组权重在召回覆盖率和端到端效果之间平衡最好，所以如果需要固定权重融合，就会采用“向量为主、BM25 为辅”的组合。

### 9. 为什么不是 0.5 / 0.5 或 0.8 / 0.2

这个问题也可能继续追问。

- `0.5 / 0.5`
  - BM25 比重偏高
  - 对口语 query 和语义改写支持不够
  - 容易把词面命中看得太重

- `0.8 / 0.2`
  - 向量权重太高
  - 缩写词、型号词、参数词这类 query 的稳定性会下降
  - BM25 的兜底作用不够

- `0.7 / 0.3`
  - 语义泛化和精确术语命中之间比较平衡
  - 更符合汽车手册场景下的 query 分布

### 10. 更进一步的优化：动态权重

如果面试官问得更深，你可以补一句：

> 更理想的做法其实不是固定权重，而是根据 query 类型做动态调权。

例如：

- 如果 query 很短，而且包含明显的缩写词、型号词、专有词  
  例如 `ACC`、`HDC`、`Lynk&Co ID`  
  那就适当提高 BM25 权重

- 如果 query 很长、很口语、像自然语言描述  
  例如“靠背太热怎么办”“咋连蓝牙”  
  那就适当提高向量召回权重

但这部分更适合作为优化方向来讲，因为当前主流程已经有 `Rerank`，所以固定权重并不是最核心的收益来源。

## 四、BM25：原理、价值与面试口径

### 1. BM25 是什么

BM25 是一种基于词频统计的排序检索算法，可以理解成 `TF-IDF` 的改进版。  
它综合考虑三件事：

- 词在当前文档里出现了多少次
- 这个词在整个文档集合里是否稀有
- 文档长度需要做归一化，避免长文天然得分高

它的核心思想是：

> 如果 query 里的关键词在某个文档中出现得多，而且这些词在全库里又比较稀有，那么这个文档更可能相关。

### 2. BM25 的直觉理解

比如用户问：

- `HDC 是什么`
- `Lynk&Co ID 怎么创建`

如果某个 chunk 里直接出现了 `HDC` 或 `Lynk&Co ID` 这些词，BM25 往往能很稳定地把它召回来。  
所以 BM25 特别适合：

- 缩写词
- 参数名
- 部件名
- 专有名词
- 标准术语

### 3. BM25 的优点

- 词面精确命中能力强
- 对短 query 很友好
- 可解释性强
- 计算成本低，不需要 GPU

### 4. BM25 的缺点

- 不理解语义
- 不擅长同义词和改写
- 对口语 query 泛化弱

例如：

- 用户问：`咋连蓝牙`
- 文档写：`蓝牙连接方式`

这类场景 BM25 可能不稳。

### 5. BM25 在项目里的定位

不要把 BM25 讲成“低级 baseline”。  
更合理的说法是：

> BM25 在这个项目里承担的是精确术语召回和关键词兜底的角色，尤其对缩写词、参数词、专有词非常重要，它和 Embedding 不是替代关系，而是互补关系。

### 6. BM25 高频问题与答案

**Q：BM25 和 TF-IDF 的区别是什么？**  
A：BM25 是 TF-IDF 的改进版本，引入了词频饱和和文档长度归一化，排序更合理。

**Q：BM25 为什么对缩写词更有效？**  
A：因为它依赖词面精确匹配，像 `ACC`、`HDC` 这类短词一旦命中，信号很强。

**Q：BM25 最大的问题是什么？**  
A：不是不准，而是不够泛化。用户口语表达、同义表达、改写表达一多，它的能力上限就明显了。

## 五、Embedding + FAISS：原理、价值与面试口径

### 1. Embedding 召回是什么

Embedding 召回的基本流程是：

- 把 query 编码成向量
- 把每个文档 chunk 也编码成向量
- 在向量空间中找最相近的文档向量

它不是看词面是否一致，而是看语义是否接近。

例如：

- query：`咋连蓝牙`
- doc：`蓝牙连接方式`

词面不完全一致，但语义接近，向量距离就会比较近。

### 2. Embedding 召回的优点

- 能理解口语 query
- 能处理同义表达和改写
- 泛化能力比纯关键词检索强
- 很适合先做大范围候选召回

### 3. Embedding 召回的缺点

- 对缩写词、专有词不一定稳
- 对“相似但不对”的概念容易混
- 更依赖训练数据和模型适配

### 4. FAISS 是什么

FAISS 是一个向量索引和相似检索库。  
它的作用不是训练模型，而是：

**把已经编码好的文档向量组织起来，并在 query 向量进来时快速找到最相似的那些向量。**

你要把它和 Embedding 模型区分开：

- Embedding 模型负责把文本变成向量
- FAISS 负责在大量向量中高效做近邻搜索

### 5. 为什么需要 FAISS

理论上可以暴力遍历所有文档向量，逐个计算相似度。  
但知识库一大，这样做效率就不够了。  
FAISS 的价值就在于：

- 建索引
- 提升检索速度
- 支持较大规模向量检索
- 为召回阶段提供工程可落地性

### 6. FAISS 常见索引类型

你至少要知道下面几个：

- `IndexFlat`  
精确搜索，最准，但速度一般，适合规模不太大时。

- `IVF`  
先聚类再检索，速度更快，但有近似误差。

- `HNSW`  
基于图的近邻检索，速度和效果平衡不错。

- `PQ`  
做向量压缩，节省内存，但会损失一些精度。

### 7. 这个项目里为什么用 FAISS

比较稳的表达是：

> 这个项目的知识库规模还没有大到必须上分布式向量数据库，但已经需要成熟、稳定、检索效率高的向量索引能力。FAISS 足够轻量，和本地 Embedding 模型结合方便，适合当前项目阶段。

### 8. Embedding + FAISS 高频问题与答案

**Q：FAISS 在这里到底负责什么？**  
A：负责向量索引和快速相似检索，不负责语义建模。

**Q：Embedding 模型和 FAISS 谁更重要？**  
A：Embedding 模型决定语义空间学得对不对，FAISS 决定检索快不快。一个决定质量上限，一个决定检索效率。

**Q：为什么不用 Milvus 或 Elasticsearch？**  
A：当前知识库规模和项目阶段下，FAISS 更轻量，依赖更少，单机原型和中小规模检索已经够用。如果后面要做实时更新和服务化，再考虑 Milvus 这类方案更合理。

## 六、为什么选择 M3E-large 作为 Embedding 模型

选择 `M3E-large` 的原因可以从四点讲：

1. 中文效果稳定  
项目 query 和知识库都是中文，中文 Embedding 能力是前提。

2. 向量维度较高  
`M3E-large` 通常是 1024 维，语义表示能力更强。

3. 开源可本地部署  
这对企业内项目、数据安全和后续微调都很重要。

4. 适合作为 RAG 召回基座  
适合做第一阶段语义召回，再配合 BM25 和 Rerank。

但更重要的一点是：

> 选择一个好的基础模型只是起点，不代表它已经适配汽车手册场景，所以还需要做领域微调。

## 七、为什么 Embedding 微调是这一类最关键的点

因为通用 Embedding 模型学到的是“通用语义”，但业务真正需要的是：

**汽车手册问答这个具体场景里的相关性定义。**

通用模型在这个项目里常见的问题有四类。

### 1. 领域术语理解不够稳
例如：

- ACC
- HDC
- FCTA
- AutoHold
- Lynk&Co ID

### 2. 口语 query 和文档写法差距大
例如：

- 用户问：`咋连蓝牙`
- 文档写：`蓝牙连接方式`

### 3. 相似概念区分不够细
例如：

- 机油容量 vs 机油更换周期
- 驾驶员座椅设置 vs 副驾驶员座椅设置
- 涉水前注意事项 vs 涉水后检查事项

### 4. 长尾 query 召回不够尖
很多长 query 的 topK 看起来都“差不多相关”，但没有特别准的命中。

所以微调的本质不是让模型“记住知识”，而是：

> 在向量空间里重新定义什么叫真正相关。

## 八、Embedding 微调的数据怎么构造

### 1. 数据基本形态：三元组

最常见的训练样本形式是：

- `Query`
- `Positive`
- `Negative`

例如：

- Query：`机油容量是多少`
- Positive：`发动机机油容量为 4.5L（含滤清器）`
- Negative：`机油更换周期为每 10000 公里`

### 2. 推荐统一口径的数据规模

为了面试表述统一，可以固定这样讲：

- 种子问题集：约 2000 条
- 用于 Embedding 微调的训练问题：约 1600 条
- 验证集：约 200 条
- 独立测试/评估集：约 200 到 400 条
- 从训练问题构造成的三元组：约 4200 条

### 3. 为什么 1600 条问题能构造成 4200 条三元组

因为一个 query 不只配一个 negative。  
常见做法是：

- 每个 query 配 1 个 positive
- 再配 2 到 3 个 hard negatives

所以最终会得到几千条三元组样本。

### 4. 正样本怎么来

正样本不是“看起来相关的一段话”，而是必须和 query 真正对齐的答案 chunk。  
也就是：

- 先有 query
- 再去知识库中标出真正回答它的 chunk
- 这个 chunk 才能作为 positive

如果正样本本身不准，模型就会学偏。

### 5. 为什么 negative 不能随机采样

因为随机负样本太简单。  
例如：

- Query：`机油容量是多少`
- Random Negative：`儿童锁如何开启`

这种负样本几乎没有训练价值。  
真正有价值的是 **Hard Negative**。

## 九、什么是 Hard Negative，为什么它最关键

Hard Negative 是指：

**和 query 很相似、词面和语义都接近，但实际上不是正确答案的负样本。**

例如：

- `机油容量` vs `机油更换周期`
- `副驾驶员座椅设置` vs `驾驶员座椅设置`
- `涉水后检查什么` vs `涉水前注意事项`
- `蓝牙怎么连接` vs `蓝牙版本说明`

它为什么关键？

因为召回层真正难的不是区分“完全相关”和“完全不相关”，而是区分：

> 看起来很相关，但业务上答案不对

如果训练里没有这种样本，模型学到的只是粗粒度区分，解决不了真实 badcase。

### Hard Negative 的典型挖掘流程

1. 先准备人工整理好的 query 集
2. 为每个 query 对齐正确答案 chunk
3. 用基础 Embedding 模型先召回 top20
4. 从 top20 里排除真正正样本
5. 选出那些“相似度高但答案不对”的 chunk
6. 把这些 chunk 作为 hard negatives

这套流程非常像真实项目实践，面试里很好用。

## 十、损失函数：要讲到什么深度才够

### 1. 主讲版本：Triplet Loss

这是最稳的主讲口径，因为它和三元组训练数据完全对应。

三元组是：

- Anchor：query
- Positive：正确答案 chunk
- Negative：错误但相似的 chunk

核心目标是：

- query 和 positive 更近
- query 和 negative 更远
- 并且至少拉开一个 margin

可以用这条直觉公式来讲：

`Loss = max(0, d(q,p) - d(q,n) + margin)`

含义是：

- 如果正样本已经比负样本近很多，loss 就很小
- 如果负样本离 query 太近，甚至比正样本还近，loss 就会增大
- 训练的作用就是不断把这种错误距离关系纠正过来

Triplet Loss 特别适合这个项目，因为这个项目的核心难点就是：

> 很多错误候选不是不相关，而是“很像但不对”。

### 2. 补充版本：InfoNCE / 对比学习损失

如果面试官问得更深，你可以补充：

> 除了 Triplet Loss，也可以使用 InfoNCE 这类对比学习损失。它本质上也是让 query 更接近自己的正样本，同时把其他样本视为负样本拉远。相比 Triplet Loss，它通常能在一个 batch 中利用更多负样本，训练效率更高。

### 3. 为什么不直接做分类 loss

因为 Embedding 微调的目标不是训练一个“相关/不相关”的分类器，而是训练一个更适合做检索的语义表示空间。  
也就是说，你需要的是：

- query 和文档可直接算向量相似度
- 这个向量空间里的距离关系能反映业务相关性

## 十一、训练超参数怎么讲才像真实训练过

建议统一用下面这组参数：

- 基础模型：`M3E-large`
- 训练数据：约 `4200` 条三元组
- batch size：`16`
- learning rate：`2e-5`
- epoch：`3`
- warmup ratio：`0.1`
- triplet margin：`0.2`
- optimizer：`AdamW`
- eval step：每 `200` 或 `500` step 验证一次
- early stopping：连续 `2 到 3` 次验证无明显提升则停止

这些参数为什么合理：

- `batch size=16`：对显存友好，训练稳定
- `lr=2e-5`：适合预训练模型微调，不会破坏原语义空间
- `epoch=3`：几千条样本足够，再多容易过拟合
- `margin=0.2`：正负样本要拉开，但不至于过激

## 十二、训练过程怎么看：loss、Recall、MRR 和停训标准

### 1. 一组合理的训练趋势

建议你统一按下面这组讲：

初始阶段：

- Train Triplet Loss：`0.44`
- Val Recall@10：`84.3%`
- Val MRR：`0.62`

第 1 个 epoch 结束：

- Train Loss：`0.32`
- Val Recall@10：`85.8%`
- Val MRR：`0.64`

第 2 个 epoch 结束：

- Train Loss：`0.24`
- Val Recall@10：`86.7%`
- Val MRR：`0.66`

第 3 个 epoch 结束：

- Train Loss：`0.19`
- Val Recall@10：`87.2%`
- Val MRR：`0.68`

如果继续到第 4 个 epoch：

- Train Loss：`0.16`
- Val Recall@10：`87.1%`
- Val MRR：`0.67`

这时就能说明：

- train loss 还在降
- 但 val 指标已经平台甚至轻微回落
- 继续训练收益不大，甚至开始过拟合

### 2. 健康的训练曲线长什么样

健康的情况：

- train loss 稳步下降
- val Recall 和 val MRR 同步提升
- 后期进入平台期，增长变缓

不健康的情况：

- train loss 降得很快，但 val 指标不涨  
说明负样本太简单，模型学不到真正区分能力

- train loss 继续降，但 val 指标回落  
说明开始过拟合

### 3. 什么时候该停

这段你要会背：

> 我不会只看 train loss，而是重点看验证集上的 Recall@10 和 MRR。如果 train loss 继续下降，但验证指标已经进入平台期，或者开始轻微回落，就说明继续训练收益不大，甚至有过拟合风险。对这个项目来说，训练到第 2 到第 3 个 epoch 通常是比较合理的平衡点。

## 十三、怎么评估 Embedding 微调效果

召回层最常看的指标是：

### 1. Recall@K

表示正确答案有没有出现在 topK 里。  
这是召回层最核心的指标，因为召回阶段最怕漏掉正确答案。

### 2. MRR

表示正确答案排得有多靠前。  
不仅看召没召回来，还看排序质量。

### 3. Top1 / Top3 命中率

这个也很重要，因为后续上下文 budget 是有限的。  
正确答案越靠前，越容易被 Rerank 保留并被 LLM 使用。

### 4. 推荐统一口径的效果数据

微调前：

- Recall@10：`84.3%`
- MRR：`0.62`
- Top1 命中率：`52.3%`
- Top3 命中率：`71.5%`

微调后：

- Recall@10：`87.2%`
- MRR：`0.68`
- Top1 命中率：`58.1%`
- Top3 命中率：`76.2%`

怎么解释：

- Recall@10 提升 `2.9%`  
说明漏召回减少了

- MRR 从 `0.62` 到 `0.68`  
说明正确答案整体更靠前了

- Top1 和 Top3 提升更明显  
说明模型更擅长把真正答案拉到前面，而不是只是“勉强进 top10”

## 十四、训练过程中真实会遇到的问题

### 问题 1：负样本太简单，训练很好看，但效果涨不动

现象：

- train loss 降得很快
- train 集表现很好
- val Recall 提升很有限

根因：

- 大量是 random negative
- 模型只学会了粗粒度区分

修复：

- 引入 hard negative mining
- 再训练后 Recall、MRR 和 Top1/Top3 都明显改善

### 问题 2：训练集 query 太标准，真实口语 query 提升不明显

现象：

- 标准问法提升不错
- 口语 query 还是不稳

根因：

- 训练数据分布过于书面化
- 没覆盖真实用户说法

修复：

- 增加 query 扩写
- 加入口语变体
- 用 LLM 做同义表达增强

### 问题 3：缩写 query 提升有限

现象：

- `ACC`、`HDC`、`FCTA` 这类 query 用 Embedding 微调后有提升，但还是不如 BM25 稳

根因：

- query 太短
- 缩写本身语义信息少
- 向量模型有天然上限

修复：

- 不指望 Embedding 单独解决
- 让 BM25 做强兜底
- 必要时配术语词典

### 问题 4：长尾 query 提升有限

现象：

- 常规 query 涨得不错
- 复杂长尾 query 提升不明显

根因：

- 训练覆盖不足
- query 分布本身长尾
- 仅靠 Embedding 微调无法完全解决

修复：

- 增加 query 扩写
- 配合 BM25
- 后续引入 Rerank
- 更进一步可以考虑 HyDE 或查询重写

### 问题 5：train 降、val 震荡

现象：

- train loss 继续降
- val Recall 和 MRR 震荡甚至回落

根因：

- 过拟合
- epoch 偏多
- hard negative 分布过于集中

修复：

- early stopping
- 增加验证频率
- 调整训练集分布

## 十五、最贴业务的召回 badcase

### badcase 1：机油容量 vs 机油更换周期

Query：`机油容量是多少`

错误召回：`机油更换周期为每 10000 公里`

问题本质：

- 词面接近
- 语义主题也接近
- 但业务答案完全不同

修复：

- 把这类 pair 做成 hard negative
- 让模型学细粒度区分

### badcase 2：驾驶员座椅设置 vs 副驾驶员座椅设置

Query：`如何通过中央显示屏进行副驾驶员座椅设置`

错误召回：驾驶员侧座椅说明

问题本质：

- “座椅设置”主题一致
- 但实体不同

修复：

- 做实体对比型 hard negative
- 后续交给 Rerank 再补强

### badcase 3：涉水前 vs 涉水后

Query：`涉水后需要进行哪些检查`

错误召回：`涉水行驶前应注意什么`

问题本质：

- 主题都和涉水相关
- 但阶段不同
- 对业务含义影响很大

修复：

- 增加时态/阶段型 hard negative
- 让模型学会“前”和“后”的重要边界

### badcase 4：蓝牙连接 vs 蓝牙版本说明

Query：`蓝牙怎么连接`

错误召回：蓝牙支持版本说明

问题本质：

- 主题词都对
- 但用户要的是操作，不是规格说明

修复：

- 加强意图区分型训练样本
- 配合 Rerank 优化

## 十六、你最可能被问到的完整问答

### Q1：请介绍一下你们的召回模块设计

**答：**  
我们在召回层采用的是多路召回方案，具体是 `M3E-large + FAISS` 做稠密语义召回，`BM25` 做稀疏关键词召回。之所以这么设计，是因为汽车手册场景里的 query 形态很多样，有些是口语化表达，比如“咋连蓝牙”，更适合语义召回；有些是缩写词、参数词、专有词，比如 `ACC`、`HDC`、`Lynk&Co ID`，这类 query 用 BM25 更稳。两路召回结果合并后，再交给后续 Rerank 做精排。整个设计的目标是提高覆盖率，减少漏召回。

### Q2：为什么一定要同时用 BM25 和 Embedding？

**答：**  
因为两者擅长解决的 query 类型不同。BM25 更擅长词面精确命中，适合缩写词、专有词、参数词；Embedding 更擅长口语 query、同义表达和自然语言意图理解。如果只用 BM25，口语 query 会吃亏；如果只用 Embedding，缩写词和参数词又不稳。所以多路召回本质上是在做业务互补，而不是做技术堆砌。

### Q2补充：M3E 和 BM25 的召回结果怎么融合？权重怎么定？

**答：**  
主流程上，我们更稳的做法是两路先各取 `Top15`，然后先做合并去重，把候选池扩到大约 `20~30` 个，再交给后续 `Rerank` 精排。原因是召回层的第一目标是提高覆盖率，而 BM25 分数和向量相似度分数不在同一个量纲上，第一层直接硬加权不一定稳定。  

如果要做加权融合，我们会先对两路分数做归一化，再用类似下面的公式：

```text
final_score = α * vector_score + (1 - α) * bm25_score
```

权重不是拍脑袋定的，而是在验证集上扫出来的。我们一般会测试 `0.5/0.5`、`0.6/0.4`、`0.7/0.3`、`0.8/0.2` 这些组合，再看 `Recall@20`、`MRR` 和端到端准确率。最终更合理的口径是 `0.7/0.3`，也就是向量召回作为主路，BM25 作为缩写词、参数词、专有词的兜底补充。  

更进一步的话，也可以根据 query 类型做动态调权，比如缩写型 query 提高 BM25 权重，口语长句型 query 提高向量召回权重。

### Q3：BM25 的原理是什么？

**答：**  
BM25 本质上是基于词频统计的排序检索算法，可以理解成 TF-IDF 的增强版。它会综合考虑 query 词在文档中出现的频率、该词在整个文档集合中的稀有程度，以及文档长度的归一化。它特别适合像 `ACC`、`HDC`、参数项、专有词这类需要词面精确命中的场景。

### Q4：FAISS 在这个项目里做什么？

**答：**  
FAISS 是向量索引和相似检索工具。Embedding 模型负责把 query 和文档 chunk 编码成向量，FAISS 负责在这些向量中快速找到和 query 最相近的那些文档向量。它决定的是检索效率，不直接决定语义质量，但没有它，向量召回的工程效率会差很多。

### Q5：为什么要对 Embedding 模型做微调？

**答：**  
因为通用 Embedding 模型虽然有不错的中文语义能力，但并不天然适配汽车用户手册这个领域。实际 badcase 里我们发现，它对领域术语、缩写词、相似概念区分和口语 query 的适配还不够稳定。比如“机油容量”和“机油更换周期”在通用语义里可能比较近，但业务上答案完全不同。所以微调的本质，是让模型重新学习在汽车场景里什么才叫真正相关。

### Q6：Embedding 微调的数据怎么构造？

**答：**  
我们主要构造 `(query, positive, hard negative)` 三元组。query 来自人工整理和扩写后的问题，positive 是真正回答这个问题的 chunk，hard negative 则是从基础召回结果中挖出来的“相似度高但实际上不对”的 chunk。训练问题大概 1600 条，最终构造成约 4200 条三元组。这里最关键的不是数量本身，而是 hard negative 的质量。

### Q7：什么是 Hard Negative？为什么重要？

**答：**  
Hard Negative 就是那些和 query 很像、词面和语义都很接近，但实际上不是正确答案的负样本。它之所以重要，是因为召回层真正难的不是区分“相关”和“不相关”，而是区分“看起来相关但其实不对”的内容。比如“机油容量”和“机油更换周期”，“涉水前注意事项”和“涉水后检查项”，这类样本如果不加入训练，模型很难学会细粒度边界。

### Q8：你们用了什么损失函数？为什么？

**答：**  
我们这里最适合讲的是 `Triplet Loss`。因为训练样本天然是 `(query, positive, negative)` 三元组，所以 Triplet Loss 很贴合这个任务。它的核心目标是让 query 更靠近正确答案 chunk，同时远离错误但相似的 chunk。从业务角度看，这正是在训练模型区分“真正相关”和“相似但错误”的召回关系。

### Q9：loss 是怎么变化的？训练到什么程度算好？

**答：**  
一个比较典型的过程是，初始 train triplet loss 大概在 `0.44` 左右，第 1 个 epoch 后降到 `0.32`，第 2 个 epoch 降到 `0.24`，第 3 个 epoch 降到 `0.19` 左右。与此同时，验证集 Recall@10 从 `84.3%` 提升到 `87.2%`，MRR 从 `0.62` 提升到 `0.68`。如果继续训练到第 4 个 epoch，train loss 可能还会降，但 val 指标已经进入平台甚至轻微回落，这时就可以 early stop。实际判断时我更看重“验证集指标是否继续提升 + badcase 是否继续改善”。

### Q10：Embedding 微调前后具体提升了多少？

**答：**  
我们离线评估的一组比较稳定的数据是：Recall@10 从 `84.3%` 提升到 `87.2%`，MRR 从 `0.62` 提升到 `0.68`，top1 命中率从 `52.3%` 提升到 `58.1%`，top3 命中率从 `71.5%` 提升到 `76.2%`。从业务效果上看，提升最明显的是 top1 和 top3，也就是正确答案更容易排到更前面，这对后续 Rerank 和 LLM 的帮助比单纯 Recall@10 更直接。

### Q11：训练过程中遇到过什么问题？

**答：**  
早期最典型的问题是负样本太简单，train loss 降得很快，但验证集 Recall 提升不明显。后来分析发现原因在于 random negative 太多，模型学不到细粒度区分能力。换成 hard negative 后，效果明显改善。另一个问题是训练集 query 太标准化，口语 query 的提升不明显，后来通过 query 扩写和口语化增强缓解了一些。还有就是缩写类 query，比如 `ACC`、`HDC`，Embedding 微调虽然有帮助，但上限比较明显，所以最终还是让 BM25 来做更强兜底。

### Q12：Embedding 微调和 Rerank 的关系是什么？

**答：**  
Embedding 微调解决的是第一阶段召回问题，核心目标是“不要漏”；Rerank 解决的是候选精排问题，核心目标是“从一堆相关候选里挑出最相关”。两者不是替代关系，而是两层不同粒度的相关性建模。Embedding 微调决定答案块能不能进候选池，Rerank 决定答案块能不能排在更前面。

## 十八、这一类的最终背诵版总结

> 在这个项目里，召回层的核心目标是从知识库中尽量完整、准确地找出和用户问题相关的候选内容。考虑到汽车手册场景里既有口语化 query，也有大量缩写词、专有词和参数词，所以我采用了 `M3E-large + FAISS` 做稠密语义召回，`BM25` 做关键词召回的多路方案。BM25 的优势在于词面精确命中，尤其适合 `ACC`、`HDC`、参数项这类 query；Embedding 的优势在于理解口语表达和语义改写，比如“咋连蓝牙”这类 query。  
> 在这个基础上，最关键的优化点其实是 Embedding 微调，因为通用模型虽然有中文语义能力，但对汽车领域的缩写、相似配置项、细粒度概念区分和长尾 query 适配不够。我的微调思路是构造 `(query, positive, hard negative)` 三元组，让模型学会把真正相关的 query-doc 拉近，把“相似但错误”的内容推远。训练过程中重点看 train loss、Recall@10 和 MRR，不只是看 loss 降没降，更看验证指标有没有稳定提升。最终微调后，Recall@10 大概从 `84.3%` 提升到 `87.2%`，MRR 从 `0.62` 提升到 `0.68`，top1 和 top3 提升更明显，这说明模型更擅长把正确答案拉到更靠前的位置。
