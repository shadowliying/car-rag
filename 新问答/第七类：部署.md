## 三、为什么选择 vLLM，而不是直接用 transformers

这是最典型的工程问法。

### 1. 直接用 transformers 的问题

如果直接用 Hugging Face `transformers` 做大模型推理，会遇到几个明显问题：

- KV Cache 利用率不高
- 多请求并发调度不够高效
- batch 不够灵活
- GPU 容易有空转和碎片浪费
- 吞吐和并发能力有限

这些问题在单条请求时可能不明显，但一旦进入服务场景，就会很明显。

### 2. vLLM 的价值

`vLLM` 的核心价值在于：

- 更高效地管理 KV Cache
- 更高效地做并发请求调度
- 更适合服务化推理
- 在同样显存资源下，通常能提供更高吞吐

所以你可以直接说：

> 我们选择 vLLM，不是因为它“新”，而是因为它更适合做大模型在线推理服务，尤其是在多并发场景下，吞吐和资源利用率优势非常明显。

## 四、PagedAttention 是什么

这是这一类最容易被问的理论点。

### 1. 先理解问题

大模型生成时，会不断积累 KV Cache。  
如果缓存管理不合理，就会出现：

- 显存碎片
- 显存浪费
- 请求之间难以高效复用空间

### 2. PagedAttention 的核心思想

`PagedAttention` 可以理解成：

**把 KV Cache 像操作系统管理内存页一样去管理，而不是给每个请求分一整块连续大内存。**

它的价值在于：

- 提高 KV Cache 利用率
- 降低显存碎片
- 支持更多并发请求
- 让显存使用更灵活

### 3. 面试里怎么讲最稳

你不需要把它讲得太底层，最稳的说法是：

> PagedAttention 的核心价值是把生成阶段最占资源的 KV Cache 做了更高效的分页管理，减少连续大块显存分配带来的浪费和碎片问题，所以在相同显存条件下，能容纳更多请求并提升整体吞吐。

---

## 五、Continuous Batching 是什么

这也是 vLLM 最高频的考点之一。

### 1. 传统 batch 的问题

传统 batch 通常是：

- 一批请求一起进
- 一起算
- 这一批结束后再处理下一批

问题是：

- 如果请求长度不同，短请求会等长请求
- GPU 资源利用不够充分
- 在线服务场景下效率不高

### 2. Continuous Batching 的核心思想

`continuous batching` 是：

**请求不是一批一批僵硬地处理，而是可以动态加入、动态退出 batch。**

这样带来的好处是：

- GPU 不容易空转
- 短请求不必长时间等别人
- 多用户并发场景下吞吐更高
- 在线服务体验更稳定

### 3. 面试里的稳妥表达

> continuous batching 的本质是动态调度请求，让不同阶段的请求共享同一批次执行，而不是静态地等整批结束再处理下一批。这样更适合在线问答服务，因为用户请求长度不一致，动态 batching 能显著提高 GPU 利用率和整体吞吐。

## 六、为什么这个项目里 LLM 才是主要性能瓶颈

这个问题你一定要会答，因为它体现你对整条链路的性能理解。

整个链路里大致有三类耗时：

### 1. Embedding 召回
相对快，尤其知识库向量已经提前建好索引。  
主要是 query 编码 + FAISS 搜索。

### 2. BM25
更快，本质是倒排和打分，开销很小。

### 3. Rerank
比 Embedding 重，因为它是 Cross-Encoder。  
但候选数通常只有 `20~30` 个，所以整体还可控。

### 4. LLM 生成
最慢，因为：

- 要逐 token 解码
- 要维护 KV Cache
- 生成长度直接影响耗时
- 多并发下资源占用最大

所以你可以直接说：

> 在这套链路里，Embedding 和 BM25 更像前处理，Rerank 是中等开销，而真正的大头是 LLM 生成。因为生成是逐 token 的自回归过程，延迟和吞吐主要都被这一层决定。

## 十、你们看哪些核心性能指标

这一块非常重要。

### 1. 首字延迟（TTFT）
也就是：

- 用户发出请求后
- 第一个 token 返回所需的时间

为什么重要？

因为这是用户最直观感受到的“系统快不快”。  
在流式输出场景里，用户不一定在乎总生成时间，但很在乎“多久开始有反应”。

### 2. 平均吞吐率
通常用：

- `token/s`

来衡量。

为什么重要？

因为这反映系统整体处理能力，尤其在多并发下更关键。

### 3. 并发能力
在高并发场景下系统是否稳定，延迟是否线性恶化。

### 4. 子服务响应时间
Embedding 和 Rerank 本身也要看，但它们更多是辅助指标。

## 十二、为什么 512 并发还能跑起来

这个问题最容易把人问住。

你可以这样答：

### 第一，vLLM 的 continuous batching 提高了 GPU 利用率
不是静态 batch，而是动态调度多请求。

### 第二，PagedAttention 改善了 KV Cache 管理
显存利用更高，更能容纳大量并发请求。

### 第三，系统是流式输出
不是所有请求都要等完整生成结束才开始返回内容。

### 第四，检索和 Rerank 不是主要瓶颈
前面模块耗时相对可控，真正的大头被 vLLM 优化了。

这段可以直接总结成：

> 能做到 512 并发，不是因为模型突然“变轻了”，而是因为 vLLM 把大模型在线推理里最关键的两个问题优化了：一是动态 batching，二是 KV Cache 管理。所以在多请求同时进来的时候，GPU 能更高效地把这些请求一起处理掉。

## 十三、Rerank 和 Embedding 的服务开销大吗

你可以按“相对量级”来讲。

### Embedding
- 基本比较轻
- 单 query 编码很快
- 不会成为主瓶颈

### Rerank
- 比 Embedding 重
- 因为是 Cross-Encoder
- 但候选数有限，一般 `20~30` 个
- 整体仍然可控

### LLM
- 最重
- 绝对瓶颈

所以比较稳的说法是：

> Embedding 几乎不构成瓶颈，Rerank 比 Embedding 更重，但总体占比仍然比较小。真正决定整个系统延迟和吞吐的，还是 LLM 生成。

## 十四、为什么 Rerank 增加 120ms 仍然值得

这个问题你前一类已经讲过，但这里可以从工程角度再说一遍。

- Rerank 耗时：`~120ms`
- 总耗时：`~2000ms`
- 占比：`6%`
- 带来端到端准确率：`+4.4%`

所以投入产出比很高。

你可以这样说：

> 从性能角度看，Rerank 只占总延迟的大约 6%，但从效果上能把系统准确率从 84.2% 提升到 88.6%，所以这是一个非常值得保留的模块。

## 十五、如果线上变慢了，你先怀疑哪里

这类问题很像真实场景。

一般排查顺序可以这样讲：

### 1. 先看生成层
因为它最可能是瓶颈：

- batch 是否过大
- 请求长度是否变长
- 平均输出 token 是否变多
- vLLM 是否打满

### 2. 再看 Rerank
例如：

- 候选数是不是变多了
- batch 推理有没有失效
- 是否掉到 CPU 了

### 3. 再看 Embedding / BM25
这两层一般不是主要瓶颈，但也要确认是否：

- 索引加载异常
- I/O 问题
- 线程配置异常

### 4. 最后看整体链路
例如：

- 网络
- 服务间调用
- 超时和重试

## 十六、如果流量暴增，怎么做降级

这道题很像工程场景题。

比较合理的答案有四层。

### 1. 减少候选数
例如：

- 召回候选从 `30` 缩到 `20`
- Rerank TopK 从 `6` 缩到 `4`

### 2. 降级 Rerank
在极端高峰下可以：

- 跳过 Rerank
- 直接用召回结果给 LLM

当然效果会降，但能保服务。

### 3. 控制生成长度
例如：

- 降低 `max_new_tokens`
- 减少长回答

### 4. 切小模型 / 分级服务
比如：

- 普通 query 用较轻配置
- 高价值 query 再走全链路

你可以这样总结：

> 如果线上流量暴增，我优先做的不是盲目扩容，而是先做有控制的降级：减少候选数、降低生成长度、必要时跳过 Rerank，先保住可用性，再看是否继续扩 GPU 资源。

## 十七、为什么首字延迟和吞吐率都要看

这是一个非常好的追问题。

### 首字延迟
反映：

- 单个用户主观体验

### 吞吐率
反映：

- 整体系统处理能力
- 高并发时单位时间能处理多少 token

只看首字延迟不够，因为：

- 系统可能很快开始说话
- 但整体生成速度很慢

只看吞吐率也不够，因为：

- 系统可能整体吞吐高
- 但单用户要等很久才看到第一个 token

所以两者必须一起看。

## 十九、这一类最可能被问到的完整问答

### Q1：为什么你们选择 vLLM，而不是直接用 transformers 部署？

**答：**  
因为这个项目是一个在线问答服务，不只是离线 demo。直接用 transformers 虽然也能跑，但在多并发场景下，KV Cache 管理、batch 调度和 GPU 利用率都不够理想。vLLM 更适合服务化推理，尤其是在多请求并发下，吞吐和资源利用率会明显更好。所以我们选 vLLM 主要是出于工程落地考虑，而不是单纯追新。

### Q2：PagedAttention 是什么？

**答：**  
PagedAttention 的核心思想是把生成时最占显存的 KV Cache 做分页式管理，有点像操作系统管理内存页，而不是给每个请求分一整块连续显存。这样可以减少显存浪费和碎片，提高 KV Cache 利用率，在同样显存条件下支持更多并发请求。

### Q3：continuous batching 是什么？

**答：**  
传统 batch 是一批请求一起进、一起出，而 continuous batching 是动态调度，请求可以持续进入和退出同一个 batch。这样可以更充分利用 GPU，特别适合在线服务，因为用户请求长度不一样，动态 batching 能减少等待、提高吞吐。

### Q4：为什么你们系统的主要瓶颈在 LLM，而不是召回或 Rerank？

**答：**  
因为 Embedding 和 BM25 主要是检索阶段，耗时相对很小；Rerank 虽然是 Cross-Encoder，但候选数一般只有 20 到 30 个，所以总体也可控。真正的大头是 LLM 生成，因为它是逐 token 自回归解码，生成长度、并发量和 KV Cache 管理都会直接影响耗时。所以整个系统的性能优化重点放在 LLM 推理层是合理的。

### Q5：你们做了哪些压测？

**答：**  
压测分成两层。第一层是子服务压测，对 Embedding 和 Rerank 服务分别做压力测试，观察不同并发下的响应时长和吞吐表现；第二层是端到端压测，用多线程 client 模拟多用户完整访问链路，看首字延迟和平均吞吐率。这样做能同时看到单模块问题和整条链路的真实性能。

### Q6：你们看哪些核心性能指标？

**答：**  
最核心的是两个：首字延迟和平均吞吐率。首字延迟反映用户主观体验，也就是系统多久开始有反应；吞吐率反映整体处理能力，特别是在高并发场景下更重要。另外也会关注不同模块的耗时拆分，比如召回、Rerank、LLM 各自占比。

### Q7：你们压测到什么水平？

**答：**  
我们最大压测并发大概做到 512，在这个并发下首字延迟大约 2 秒左右，吞吐率大概 12k token/s。链路拆分上，BM25 约 10ms，向量召回约 30ms，Rerank 约 120ms，LLM 生成约 1800ms，总体响应大约 2 秒级别。

### Q8：4 卡 V100 的部署意义是什么？

**答：**  
7B 模型本身单卡也能跑，但如果要做服务化、追求更高并发和吞吐，多卡部署会更稳。这个项目里 4 卡部署的核心价值不是“把模型塞进去”，而是提高整体服务容量，让在高并发下首字延迟和吞吐还能维持在一个可接受范围内。

### Q9：Rerank 增加了 120ms，值得吗？

**答：**  
很值得。因为 Rerank 的耗时占整个 2 秒级响应的大约 6%，但它能把端到端准确率从 84.2% 提升到 88.6%，总提升 4.4%。从工程投入产出比看，这是一个非常划算的模块。

### Q10：如果线上流量暴增，你会怎么降级？

**答：**  
我会优先做有控制的降级，而不是直接让服务雪崩。比如先减少召回候选数和 Rerank TopK，控制生成长度，必要时在高峰期跳过 Rerank 直接走召回+LLM，先保住系统可用性。如果流量持续高，再看是否补更多 GPU 资源或调整服务分层。

### Q11：为什么首字延迟和吞吐率都要看？

**答：**  
因为它们代表的是两件不同的事。首字延迟代表单用户的主观响应体验，吞吐率代表整个系统在并发下的处理能力。只看其中一个都会片面，所以我们压测时一定是把两者结合看。

### Q12：Docker 在这个项目里主要解决什么问题？

**答：**  
Docker 主要解决的是环境交付问题，比如依赖统一、部署一致性和服务可复现。它不是算法优化手段，但对于这种包含 Embedding、Rerank、LLM 和 benchmark 的系统来说，环境统一非常重要。

## 二十一、这一类的最终背诵版总结

> 在这个项目里，部署和性能优化的重点不是“让模型能跑”，而是让整个问答系统在并发场景下稳定、可控地跑起来。我们最终采用了 vLLM 来部署 Qwen-7B-Chat，而不是直接用 transformers，主要因为 vLLM 更适合服务化推理，在 KV Cache 管理和多请求调度上效率更高。它的两个关键机制是 PagedAttention 和 continuous batching，前者提升了 KV Cache 的显存利用率，后者让不同阶段的请求可以动态共享 batch，从而提高 GPU 利用率和整体吞吐。  
> 在性能上，我们把压测分成子服务和端到端两层，重点关注首字延迟和平均吞吐率。最大并发大约做到 512，首字延迟大约 2 秒，吞吐率大约 12k token/s。链路拆分上，BM25 约 10ms，向量召回约 30ms，Rerank 约 120ms，而 LLM 生成约 1800ms，所以生成层才是真正瓶颈。Rerank 虽然增加了一点延迟，但只占整体 6%，却带来了 4.4% 的准确率提升，因此工程上非常值得保留。这个项目的核心不是只把模型跑起来，而是把“效果、延迟、吞吐和成本”一起平衡好。
