# 第四类：Rerank 重排模块与 Rerank 微调

这一类是整个项目里最容易体现“你到底有没有真的做深”的地方。  
因为很多人会讲：

- 召回用了 `M3E + BM25`
- 最后加了一个 `BGE-reranker`

但真正会被面试官追问的是：

- 为什么召回之后还需要 `Rerank`
- `Bi-Encoder` 和 `Cross-Encoder` 到底差在哪
- 为什么 `Cross-Encoder` 更适合精排，不适合海量召回
- 你们为什么选 `BGE-reranker-large`
- 微调到底做了没有，做了什么，为什么一开始效果不好
- `Pointwise / Pairwise / Listwise` 你怎么选
- 为什么最后用了 `BCE Loss`
- 微调数据怎么构造
- `Hard Negative` 在 Rerank 里是怎么用的
- 微调前后到底提升了多少
- 训练时 `loss` 是怎么变化的，什么时候停
- 线上增加了多少延迟，值不值得

所以这一类不能讲成一句“召回后加了重排，效果更好”。  
你要讲成：

**多路召回负责海选，Rerank 负责精排；而 Rerank 微调的核心，是让模型学会识别那些“很像但其实不对”的候选文档。**

---

## 一、这一类你要掌握到什么程度

你至少要做到：

1. 能讲清为什么召回后还要做 Rerank。
2. 能讲清 `Bi-Encoder` 和 `Cross-Encoder` 的本质区别。
3. 能讲清 `BGE-reranker-large` 为什么适合这个项目。
4. 能讲清为什么 Rerank 只处理少量候选，而不是直接做全库检索。
5. 能讲清 Rerank 微调为什么重要，而且比“加不加一个 Rerank 模型”更值得深挖。
6. 能讲清 `Pointwise / Pairwise / Listwise` 的区别和取舍。
7. 能讲清为什么最终采用 `Pointwise + BCE Loss`。
8. 能讲清微调数据怎么构造，尤其是 Hard Negative。
9. 能讲清微调前后指标变化、loss 变化和停训标准。
10. 能讲清训练过程中踩过的坑和修法。
11. 能把这些内容和实际汽车手册业务问题绑起来。

---

## 二、Rerank 在整个系统里的位置是什么

整个系统的检索链路可以理解成：

- 多路召回：先把可能相关的候选尽量全拿回来
- Rerank：再从候选里精细排序
- LLM：只读取前面最相关的少量上下文来生成答案

比较清晰的流程是：

- `BM25 Top15`
- `Embedding Top15`
- 合并去重后大概得到 `20~30` 个候选 chunk
- `BGE-reranker-large` 对这 `20~30` 个候选逐个打分
- 取 `Top6` 送给 LLM
- LLM 基于这 `Top6` 生成答案

这里面 Rerank 的定位非常明确：

> 它不是为了扩大召回范围，而是为了把“已经召回到的候选”重新排得更准。

---

## 三、为什么召回之后还要 Rerank

这是高频必问题。

核心原因是：

**召回和重排的目标不同，模型架构也不同。**

### 召回阶段的目标
目标是：

- 快
- 广
- 不漏

所以召回阶段更像“海选”，宁可多拿一些候选，也别漏掉真正答案。

### Rerank 阶段的目标
目标是：

- 更细
- 更准
- 把最相关的内容顶到前面

它更像“精选”。

### 为什么单靠召回不够
因为多路召回虽然提高了覆盖率，但也会带来更多“看起来相关”的候选。  
比如用户问：

- `如何开启座椅加热`

召回出来的可能有：

- 座椅加热开启方式
- 座椅通风说明
- 空调温度调节
- 座椅舒适性设置
- 驾驶员座椅记忆功能

这些内容都和“座椅”有关，但真正该排第一的只有少数几段。  
Rerank 的作用，就是把真正最贴近 query 意图的那几个候选排到最前面。

---

## 四、Bi-Encoder 和 Cross-Encoder 的本质区别

### 1. Bi-Encoder 是什么

Bi-Encoder 的做法是：

- Query 单独编码成向量
- Doc 单独编码成向量
- 最后再算两个向量的相似度

这就是召回阶段常用的结构，比如 `M3E`。

它的优点是：

- 可以提前把所有文档都编码好
- 检索速度快
- 适合海量文档召回

缺点是：

- Query 和 Doc 在编码时没有发生充分交互
- 对细粒度差异的辨别能力有限

### 2. Cross-Encoder 是什么

Cross-Encoder 的做法是：

- 把 `Query` 和 `Doc` 拼成一条输入
- 一起送进 Transformer
- 直接输出这对 `(Q, D)` 的相关性得分

例如：

- `[CLS] query [SEP] doc [SEP]`

这样 Query 和 Doc 从一开始就在同一个编码过程中发生注意力交互。  
所以它能更细地判断：

- query 真正想问什么
- doc 是不是正好在回答这个问题
- 这个 doc 只是主题相关，还是答案级相关

### 3. 为什么 Cross-Encoder 更准

因为它是“早期交互”。  
也就是 Query 和 Doc 在每一层 Transformer 里都能互相看见对方。  
相比之下，Bi-Encoder 是“后期交互”，先各自编码，再靠一个相似度做比较。

这会带来一个关键差异：

> Bi-Encoder 更擅长粗粒度相关性判断，Cross-Encoder 更擅长细粒度相关性判断。

### 4. 为什么 Cross-Encoder 不能直接做全库召回

因为它太慢。  
如果知识库有几万甚至几十万 chunk，你不可能让用户每来一个 query，就把 query 和全库每个 chunk 拼接跑一遍 BERT。  
所以它只能用于：

- 召回后的小候选集精排

也就是：

- 先用 Bi-Encoder / BM25 海选
- 再用 Cross-Encoder 精选

---

## 五、Rerank 为什么对 RAG 特别重要

RAG 的后半段是 LLM 生成。  
而 LLM 对输入上下文非常敏感：

- 上下文太少，答案不全
- 上下文太多，重点被稀释
- 上下文错了，答案会被带偏

所以 Rerank 的真正价值，不只是“排序变好”，而是：

**它提升了送给 LLM 的上下文质量。**

你可以把它理解成三点：

1. 把真正相关的 chunk 顶到前面
2. 把相似但不对的 chunk 筛掉
3. 缩短送入 LLM 的上下文，减少噪音

所以在业务上，Rerank 的价值体现在：

- 回答更聚焦
- 更少跑偏
- 更少混淆相似概念
- 更少把错误上下文塞给大模型

---

## 六、为什么选择 BGE-reranker-large

项目里最稳的口径是：

**Rerank 使用的是 `BGE-reranker-large`。**

你可以从四个角度讲。

### 1. 它是典型的 Cross-Encoder 结构
非常适合做重排，不适合做大规模召回，但非常适合做候选精排。

### 2. 中文场景表现好
这个项目是中文汽车手册问答，所以中文能力很重要。  
`BGE-reranker-large` 在中文相关性判断任务上表现比较稳。

### 3. 开源可本地化部署
相比一些收费 API 模型，本地部署更方便，也更适合后续微调。

### 4. 精度和速度平衡合理
从项目文档里的对比口径可以统一成：

- `bge-reranker-base`：更快，但精度略低
- `bge-reranker-large`：精度和速度平衡最好
- 更大的 2B 类模型：精度再高一点，但成本太重

可以直接这样说：

> 我们最终选 `bge-reranker-large`，因为它在中文相关性判断上效果比较稳，精度比 base 更好，但延迟和资源占用又还在业务可接受范围内，是一个比较均衡的选择。

---

## 七、为什么取 Top6 给 LLM

这是面试里很实用的点。

原因有三点：

1. LLM 上下文预算有限  
不是塞得越多越好。

2. 太多上下文会稀释重点  
尤其在问答场景里，LLM 很容易在多个相似段落之间混合总结。

3. Rerank 后 Top6 通常已经能覆盖答案  
这个项目的经验口径就是：  
经过 Rerank 精排后，`Top6` 基本足够覆盖高质量答案。

所以这不是一个随便拍脑袋的数字，而是：

> 在精度、上下文长度和推理成本之间做的工程折中。

---

## 八、Rerank 微调为什么是这一类最重要的部分

单纯“加一个通用的 Rerank 模型”当然会有提升。  
但真正能体现你项目深度的，是：

**你有没有让 Rerank 模型学会这个领域里什么叫“真正相关”。**

因为通用 Reranker 虽然已经具备一般相关性判断能力，但在汽车手册这种场景里仍然会遇到下面几类问题：

### 1. 相似主题混淆
例如：

- 机油容量 vs 机油更换周期
- 涉水前注意事项 vs 涉水后检查事项
- 驾驶员座椅设置 vs 副驾驶员座椅设置

### 2. 同一主题下不同意图混淆
例如：

- 蓝牙连接方式 vs 蓝牙版本说明
- 空调温度调节 vs 座椅加热开启

### 3. query 口语化但候选文本很书面
这会导致通用 Reranker 不一定总能把真正答案排在第一。

所以 Rerank 微调的本质是：

> 让模型学会在汽车领域里，哪些候选只是“主题沾边”，哪些候选才是“真正回答这个问题”。

---

## 九、Pointwise、Pairwise、Listwise：面试一定会问

### 1. Pointwise 是什么

把每个 `(Query, Doc)` 当成一个独立样本，直接预测：

- 相关
- 不相关

或者输出一个相关性分数。

例如：

- `(Q, D1) -> 0.92`
- `(Q, D2) -> 0.63`
- `(Q, D3) -> 0.18`

最后按分数排序。

### 2. Pairwise 是什么

不是单独判断每个 doc，而是比较两个 doc：

- 对同一个 query，`D1` 和 `D2` 谁更相关

它更强调相对排序。

### 3. Listwise 是什么

直接把一个 query 对应的一组候选文档看成一个整体，学习整组候选的排序。

### 4. 为什么最终采用 Pointwise

这是你要讲得最稳的地方。

虽然从排序任务的理论上，Pairwise 和 Listwise 更“像排序”，但在这个项目里最终采用 `Pointwise`，原因是：

1. 数据最容易构造  
只需要 `(query, doc, label)`。

2. 和 `BGE-reranker-large` 原生结构更匹配  
它本身就是一个 sequence classification 风格的相关性打分模型。

3. 工程实现简单、训练稳定  
尤其在样本量不大的时候更容易控制。

4. 在当前业务里效果已经足够好  
没有必要为了更复杂的训练框架增加实现复杂度。

### 5. 为什么没最终采用 Listwise

这是非常像真实做过的回答点。

项目里其实可以讲：

- 前期考虑过 listwise 思路
- 但实际遇到两个问题

第一，数据标注难度更高  
因为不是标 0/1 就够了，而是要给同一 query 的多个候选建立更完整、更细的排序关系。

第二，数据区分度不够时，loss 不好下降  
很多候选都“有点相关”，但很难稳定标出细粒度排序，训练反而不稳定。

所以最终项目上更可落地的是：

> 用 Pointwise 二分类先把“相关”和“不相关”边界学清楚，再通过推理分数完成排序。

## 十、Rerank 微调数据怎么构造

这一块是最容易被追问的重点之一。

### 1. 最终统一口径的数据规模

建议你固定讲下面这组：

- 核心人工标注 query：约 `200` 条
- 每个 query 标注约 `3` 个候选
- 总标注样本：约 `600` 条
- 正样本：约 `200`
- 负样本：约 `400`
- 正负比例：`1:2`

这组数字和现有项目资料最一致，也最好记。

### 2. 数据不是凭空写出来的

最靠谱的说法是：

> Rerank 微调数据不是直接手写“query 对应什么答案”，而是从真实召回结果里构造出来的。

也就是：

1. 先准备一批真实业务 query
2. 用当前召回系统取出每个 query 的候选集
3. 对候选集做人工标注
4. 标出哪些候选真正相关，哪些只是看起来相关
5. 必要时再补一些 Hard Negative

这样做的好处是：

- 数据和实际线上问题分布更接近
- 候选更真实
- 标出来的负样本更有训练价值

### 3. 为什么正负比例是 1:2

因为真实召回结果里，本来就通常是：

- 少数正确候选
- 多数错误候选

所以 1:2 比例比 1:1 更贴近真实分布，也更有利于模型学会筛掉错误候选。

---

## 十一、Rerank 里的 Hard Negative 为什么更重要

在 Embedding 微调里，Hard Negative 已经很关键；  
在 Rerank 微调里，它更关键，因为 Rerank 的任务本身就是：

**在一堆“都像那么回事”的候选里，找出最对的那个。**

典型 Hard Negative 例子：

- Query：`机油容量是多少`
- Positive：`发动机机油容量为 4.5L`
- Hard Negative：`机油更换周期为每 10000 公里`

- Query：`涉水后需要检查哪些项目`
- Positive：`检查制动器、喇叭、转向助力、外部车灯`
- Hard Negative：`涉水前注意事项`

- Query：`如何通过中央显示屏进行副驾驶员座椅设置`
- Positive：副驾座椅设置说明
- Hard Negative：驾驶员座椅设置说明

Rerank 微调最核心的收益，就来自于它更擅长识别这类“很像但不对”的候选。

这一点你可以直接背：

> Rerank 微调真正提升的不是粗粒度相关性，而是 Hard Negative 的识别能力。

---

## 十二、损失函数为什么最终选择 BCE Loss

这是这类里面最重要的技术追问之一。

### 1. 为什么用 BCE

因为最终采用的是 `Pointwise` 二分类方案。  
也就是把每个 `(query, doc)` 样本标成：

- `1`：相关
- `0`：不相关

这种任务最自然的损失函数就是：

**BCE（Binary Cross Entropy）**

### 2. BCE 的直觉是什么

模型会输出一个相关概率 `p`。  
如果标签是 `1`，就希望 `p` 越接近 1 越好。  
如果标签是 `0`，就希望 `p` 越接近 0 越好。

也就是说：

- 相关样本打高分
- 不相关样本打低分

这和 Rerank 的目标非常一致。

### 3. 为什么 BCE 特别适合这个项目

因为这个项目里你最容易稳定拿到的是：

- `(Q, D)` 是否相关

而不是：

- 完整的 listwise 排序标签
- 大量高质量 pairwise 偏序对

所以从数据现实出发，BCE 是最合适、最稳的方案。

### 4. 为什么不用 Triplet Loss

Triplet Loss 更适合 Embedding 微调，因为它训练的是向量空间距离。  
但 Rerank 这里是 Cross-Encoder 直接做 `(Q, D)` 相关性打分，更自然的是二分类损失。

### 5. 为什么不用 ListNet / LambdaRank

不是不能用，而是当前项目不划算：

- 需要更高质量的排序标注
- 数据构造更复杂
- 工程复杂度更高
- 当前数据量不大，Pointwise 已经足够有效

所以最终结论是：

> 在这个项目的数据规模和工程约束下，Pointwise + BCE 是性价比最高的选择。

## 十三、训练超参数和训练设置怎么讲

建议统一用下面这组：

- 基础模型：`BGE-reranker-large`
- 训练方式：`Pointwise 二分类微调`
- 样本量：`约 600 条人工标注 pair`
- 正负比例：`1:2`
- batch size：`16`
- learning rate：`2e-5`
- epochs：`3`
- warmup ratio：`0.1`
- weight decay：`0.01`
- max length：`512`
- optimizer：`AdamW`
- 训练精度：`FP16`

为什么这组参数合理：

- 数据量小，`3 epoch` 足够，再多容易过拟合
- `2e-5` 是 BERT 类模型微调的常见稳定学习率
- `batch size=16` 兼顾显存和稳定性
- `weight decay=0.01` 用来压过拟合
- `max length=512` 与模型本身能力匹配

---

## 十四、Rerank 训练时 input 长什么样

这个也很常被问。

训练输入不是单独的 query，也不是单独的 doc，而是：

- `(query, doc)` 对

通常格式是：

- `[CLS] query [SEP] doc [SEP]`

模型读完这整条拼接后的输入，输出一个相关性 logit。

你可以这样说：

> Rerank 和 Embedding 最大的不同，就是它不是把 query 和 doc 分开编码，而是把它们拼在一起，让模型在编码阶段就发生充分交互，最后直接输出相关性分数。

---

## 十五、长文本怎么处理

因为 `BGE-reranker-large` 通常最大支持 `512 tokens`，所以长 chunk 是实际问题。

比较稳的表达方式：

1. 前面知识库构建阶段已经尽量控制 chunk 长度  
不会一上来把特别长的原始整页直接塞给 Rerank。

2. Rerank 阶段再做 `max_length=512` 截断  
保证输入合法。

3. 如果文档特别长，优先保留和标题/主题强相关的片段  
避免把最有信息量的部分截掉。

这一段的关键不是炫复杂，而是要体现：

> 你知道 Cross-Encoder 对输入长度更敏感，所以前面的分块设计和这里的截断策略要配合。

---

## 十六、训练过程中的 loss、停训标准和怎么判断训练健康

这部分要讲得像真的训过，而不是“跑了一下脚本”。

### 1. 可以统一使用的一组训练趋势

你可以按下面这组口径讲：

初始阶段：

- Train BCE Loss：`0.68`
- Val Loss：`0.52`

第 1 个 epoch 结束：

- Train Loss：`0.43`
- Val Loss：`0.46`

第 2 个 epoch 结束：

- Train Loss：`0.31`
- Val Loss：`0.41`

第 3 个 epoch 结束：

- Train Loss：`0.24`
- Val Loss：`0.40`

如果继续到第 4 个 epoch：

- Train Loss：`0.18`
- Val Loss：`0.42`

这时候就说明：

- train loss 还在降
- 但 val loss 已经不再改善，甚至轻微回升
- 继续训练开始有过拟合风险

### 2. 健康的训练过程长什么样

健康情况：

- train loss 稳步下降
- val loss 也下降或趋于平稳
- Precision / F1 / NDCG 逐步提升

不健康情况：

- train loss 很快降下去，但 val 指标不涨  
通常说明数据太简单

- train loss 降，val loss 上升  
说明开始过拟合

### 3. 什么时候停训

你可以固定说：

> 对 Rerank 这种小数据量微调，我不会追求把 train loss 压到最低，而是更关注验证集上的 Precision、F1 和排序指标。如果训练到第 3 个 epoch 左右，验证集指标已经平台甚至轻微回落，就会 early stop。这个项目里 3 个 epoch 基本是一个比较合适的平衡点。

## 十七、Rerank 微调前后效果怎么讲

这一部分要统一一套数字口径。

### 1. Rerank 模型本身的指标

微调前：

- Accuracy：`82.3%`
- Precision：`78.5%`
- Recall：`85.2%`
- F1：`81.7%`

微调后：

- Accuracy：`86.5%`
- Precision：`80.5%`
- Recall：`86.8%`
- F1：`83.5%`

最值得强调的是：

- `Precision +2%`
- Accuracy、F1 也都有提升

### 2. 端到端系统效果

这个更重要，因为面试官更关心最终业务价值。

- 无 Rerank：`84.2%`
- 有 Rerank 但未微调：`86.6%`
- 有 Rerank 且微调后：`88.6%`

所以可以这样理解：

- 单纯加 Rerank：`+2.4%`
- Rerank 再微调：总共 `+4.4%`

### 3. 怎么解释这些提升

你要重点强调：

> 微调后 Precision 提升最明显，这说明模型更擅长识别 Hard Negative，也就是更会区分“主题相关”和“答案真正相关”的差别。

这比泛泛说“效果变好了”强很多。

## 十八、训练过程中真实遇到的问题

这部分最像实战经验。

### 问题 1：开源数据几乎没效果

现象：

- 微调后指标几乎不变

原因：

- 开源数据和汽车手册问答场景分布差异太大
- 模型本身可能已经见过类似通用数据

解决：

- 改用领域真实数据
- 从真实召回候选中人工标注

### 问题 2：自己构造的正负样本太简单

现象：

- loss 很快下降
- 训练集效果很好
- 验证集提升有限
- 初期可能只有 `+0.5%` 左右提升

原因：

- 正负例差异太大
- 模型没有学到真正困难的边界

解决：

- 加入 Hard Negative
- 从“模型当前容易判错的候选”里挖难负样本

项目里很值得你讲的一句是：

> 加入 Hard Negative 之后，Precision 的提升才从早期的 `+0.5%` 变成后面的 `+2%`。

### 问题 3：尝试 listwise 但 loss 不好降

现象：

- 训练不稳定
- 排序边界学不清
- loss 降得不明显

原因：

- 标注数据没有足够细的排序区分度
- 很多候选“都有点相关”，但很难标成清晰的多等级排序

解决：

- 回到 Pointwise 二分类
- 先把相关/不相关边界学清楚

### 问题 4：过拟合

现象：

- train loss 持续下降
- val loss 回升
- 验证集指标不再涨

原因：

- 数据量只有 600 条左右
- 模型参数量较大

解决：

- epoch 控制在 3
- 加 `weight_decay`
- 适当 early stopping

### 问题 5：标注标准不一致

现象：

- 指标波动
- 某些边界 case 前后判断不一致

原因：

- 不同标注人对“相关”的理解不完全一致

解决：

- 制定标注规范
- 做交叉复核
- 对边界样本统一规则

## 二十、Rerank 会增加多少延迟，值不值得

这是高频工程题。

可以统一按这组数据讲：

- BM25 召回：`~10ms`
- 向量召回：`~30ms`
- Rerank（30 个候选）：`~120ms`
- LLM 生成：`~1800ms`
- 总体响应：`~2000ms`

所以 Rerank 的耗时占比大概是：

- `6%`

但换来的收益是：

- 系统准确率从 `84.2%` 提升到 `88.6%`
- 总提升 `4.4%`

所以这个投入产出比非常高。

你可以直接背：

> Rerank 的延迟大概 120ms，占整个 2s 级响应里的 6% 左右，但它能带来 4.4% 的端到端准确率提升，所以从工程上看非常值得。

## 二十一、如果 Rerank 太慢，怎么优化

这类题非常像面试官会顺手追问的场景题。

### 1. 控制候选数
不要让 Rerank 去处理 `100+` 个候选。  
在项目里，通常控制在 `20~30` 个候选比较合理。

### 2. 批量推理
不要一个 `(Q, D)` 一个 `(Q, D)` 地跑。  
把多个 pair 一次性 batch 输入模型。

### 3. 用 FP16
推理时半精度能明显节省显存并提速。

### 4. 选择更小模型
如果线上延迟压力非常大，可以从 `large` 换成 `base`，用一定精度换速度。

### 5. 多阶段级联
例如：

- 轻量 Reranker 先筛到 Top20
- 重量 Reranker 再筛到 Top6

### 6. 流量高峰时降级
极端情况下可以直接跳过 Rerank，退回到“仅召回+LLM”的降级方案。

## 二十二、你最可能被问到的完整问答

### Q1：为什么召回后还需要 Rerank？

**答：**  
因为召回和重排的目标不一样。召回阶段的目标是快和不漏，宁可多拿一些候选；而重排阶段的目标是更细地判断哪几个候选才是真正回答当前 query 的内容。汽车手册场景里很多候选都主题相关，但只有少数是答案级相关，Rerank 就是把这些真正最相关的内容排到前面，再交给 LLM。

### Q2：Bi-Encoder 和 Cross-Encoder 的区别是什么？

**答：**  
Bi-Encoder 是 query 和 doc 分开编码，再算相似度，适合召回，优点是快；Cross-Encoder 是把 query 和 doc 拼在一起编码，直接输出相关性分数，适合精排，优点是更准。因为 Cross-Encoder 在编码阶段就让 query 和 doc 充分交互，所以对细粒度差异的判断能力更强，但代价是速度慢，不能做全库检索。

### Q3：为什么 Cross-Encoder 更适合精排而不适合召回？

**答：**  
因为它要对每个 `(Q, D)` 对做一次完整前向传播。如果全库有几万甚至几十万 chunk，这样算不现实。但如果只是对召回后的 20 到 30 个候选做排序，它的精度优势就很值得。所以 Cross-Encoder 更适合“精选”，不适合“海选”。

### Q4：你们为什么选 BGE-reranker-large？

**答：**  
因为它是比较成熟的中文 Cross-Encoder 重排模型，在中文相关性判断任务上效果稳定，开源可本地部署，也方便后续微调。和 base 相比，它精度更好；和更大的 2B 类模型相比，它的延迟和显存成本又更可控。对我们这个项目来说，`bge-reranker-large` 是精度和工程成本比较平衡的选择。

### Q5：Rerank 微调为什么重要？

**答：**  
因为通用 Reranker 虽然已经有一定相关性判断能力，但在汽车手册场景里，很多错误候选不是完全不相关，而是“很像但不对”。比如机油容量和机油更换周期、涉水前注意事项和涉水后检查事项、驾驶员座椅和副驾驶员座椅设置。Rerank 微调的核心价值，就是让模型学会更好地区分这类 Hard Negative。

### Q6：你们 Rerank 微调用的是 Pointwise、Pairwise 还是 Listwise？

**答：**  
最终采用的是 Pointwise，也就是把每个 `(query, doc)` 当成一个二分类样本，判断它相关还是不相关。我们之所以这么选，是因为 Pointwise 和 `BGE-reranker-large` 的结构更匹配，数据构造最直接，工程实现也最稳定。Listwise 和 Pairwise 理论上更贴近排序任务，但对数据标注要求更高，在当前项目的数据规模下性价比不高。

### Q7：为什么最终选择 BCE Loss？

**答：**  
因为我们最终采用的是 Pointwise 二分类方案，每个 `(query, doc)` 只有相关或不相关两个标签。BCE Loss 正好对应这个任务：正样本希望打高分，负样本希望打低分。相比之下，Triplet Loss 更适合 Embedding 微调，ListNet 或 LambdaRank 这类排序损失则需要更高质量、更细粒度的排序标注，在这个项目里不划算。

### Q8：Rerank 微调数据是怎么构造的？

**答：**  
不是直接手写问答，而是从真实召回结果里构造出来的。我们先准备一批真实 query，用当前召回系统给每个 query 拿出候选集，再对这些候选做人工标注，区分哪些是真正相关，哪些只是主题接近。最后大概标了 200 个 query，总共约 600 条 `(query, doc, label)` 样本，正负比例是 1:2。除此之外，还补了一些 Hard Negative，让模型更会区分“很像但不对”的候选。

### Q9：训练过程中 loss 是怎么变化的？什么时候停？

**答：**  
比较典型的情况是，初始 train BCE loss 大概在 0.68 左右，第 1 个 epoch 降到 0.43，第 2 个 epoch 降到 0.31，第 3 个 epoch 降到 0.24。与此同时，验证集 loss 先下降到大概 0.40 附近，之后如果继续训练可能会轻微回升。这说明模型开始进入平台期甚至出现过拟合风险，所以我们通常在第 3 个 epoch 左右停掉，而不是追求把训练 loss 压到最低。

### Q10：Rerank 微调前后提升了多少？

**答：**  
Rerank 模型本身的指标上，Accuracy 从 82.3% 提升到 86.5%，Precision 从 78.5% 提升到 80.5%，Recall 从 85.2% 提升到 86.8%，F1 从 81.7% 提升到 83.5%。更重要的是端到端系统效果：无 Rerank 时准确率是 84.2%，加未微调 Rerank 后是 86.6%，加微调后的 Rerank 后达到 88.6%，总共比无 Rerank 提升了 4.4%。

### Q11：微调过程中遇到过什么问题？

**答：**  
最开始用开源数据做，效果几乎没提升，因为和汽车手册场景分布差太远。后来自己构造了一些简单正负样本，发现 loss 降得很快，但提升只有 0.5% 左右，说明数据太简单了。再后来改成从真实召回候选里人工标注，并增加 Hard Negative，效果才明显改善，Precision 的提升到了 2%，端到端准确率也更稳。

### Q12：Rerank 的延迟值得吗？

**答：**  
很值得。我们这里 Rerank 对 30 个候选做精排，大概增加 120ms 左右延迟，占整个 2s 左右响应时间的大约 6%，但它带来了 4.4% 的端到端准确率提升。从投入产出比上看非常高，所以这个模块是值得保留的。

## 二十三、这一类最容易犯的错误

1. 把 Rerank 讲成“排序更准”，但说不清为什么更准。
2. 分不清 Bi-Encoder 和 Cross-Encoder。
3. 不会解释为什么 Cross-Encoder 不能做全库召回。
4. 只说“用了 BGE-reranker-large”，不会讲为什么选它。
5. 微调部分只说“做了”，但讲不清 Pointwise / BCE / Hard Negative。
6. 说做过 listwise，但说不清为什么后来放弃。
7. 不会讲 loss 曲线、停训标准和过拟合现象。
8. 只报模型指标，不报端到端业务指标。
9. 不会把 Hard Negative 和真实业务问题对应起来。
10. 不会解释 Rerank 增加延迟后为什么仍然值得。

## 二十四、这一类的最终背诵版总结

> 在这个项目里，Rerank 的作用是对多路召回出来的候选结果做精细排序，把真正最相关的少量文档筛出来交给 LLM。召回阶段用的是 Bi-Encoder 或 BM25，重点是快和不漏；Rerank 用的是 `BGE-reranker-large` 这种 Cross-Encoder，重点是更细粒度地判断 query 和 doc 是否真正匹配。它之所以更准，是因为 query 和 doc 在编码阶段就发生了充分交互，所以更擅长识别“主题相关但答案不对”的候选。  
> 真正关键的优化点在于 Rerank 微调。我们最终采用的是 Pointwise 二分类方案，用 `(query, doc, label)` 数据微调 `BGE-reranker-large`，损失函数采用 BCE。数据不是随便写出来的，而是从真实召回候选中人工标注得到的，大概 200 个 query、600 条样本，正负比例 1:2，并重点加入了 Hard Negative。微调后，Rerank 自身 Precision 提升了 2%，端到端系统准确率从 84.2% 提升到 88.6%。工程上虽然增加了大约 120ms 延迟，但只占整体响应的 6%，换来 4.4% 的端到端准确率提升，投入产出比很高。
